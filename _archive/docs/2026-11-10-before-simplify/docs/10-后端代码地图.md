### 1.1 为什么 kernel 有 97 个模块

不是过度设计，而是**按领域拆分的结果**：`system.rs` 原文件约 7,900 行，
按「身份 / 组织 / 安全 / 租户 / 审计 / 计费」拆成现在的粒度。

**代价也是真实的**：97 个模块里有 15 个超过 AGENTS 规定的 300 行（见 §8）。

## 2. 启动流程（逐步骤对应代码）

### 2.1 `main` 的七步

| 步 | 位置 | 做什么 | 失败行为 |
|---|---|---|---|
| 0 | `main.rs` `--healthcheck` | TCP 连 `BIND_ADDR`，2s 超时 | 退出码 1 |
| 0 | `main.rs` `--dump-openapi` | 合并插件契约打到 stdout | 退出码 1 |
| 1 | `Config::load` | TOML + 环境变量 + `validate()` | **写 stderr 后退出**（日志还没装） |
| 2 | `init_tracing` | EnvFilter + 格式化 + 可选 OTel | OTel 失败只降级，不阻断 |
| 3 | `kernel::app::build` | 建池 → 迁移 → 插件 → 路由 → 中间件 → 后台任务 | 整体失败 |
| 4 | `TcpListener::bind` | 绑定端口 | 退出 |
| 5 | `axum::serve` | `into_make_service_with_connect_info` | — |
| 6 | 停机收尾 | 关连接池 → flush OTel | — |

> **为什么配置在日志之前**：OTLP 端点与采样率来自配置，而订阅器只能 `init()` 一次。
> 配置错误的可观测性由 `anyhow::Result` 的 `Debug` 打到 stderr 保证。

### 2.2 `app::build` 的装配顺序

```
1. metrics::install()                       幂等，必须在使用前
2. db::connect()                            建池（min 5 预热，每连接下发超时）
3. ensure_schema("sys") + KERNEL_MIGRATOR   内核迁移
4. plugin::load_plugins()                   收集 → 校验 → 拓扑排序
5. 逐插件：
     ensure_schema(id) + 插件迁移
     sync_plugin_permissions()              权限点 upsert（代码是唯一来源）
     sync_plugin_menus()                    菜单幂等写入**每个租户**
6. system::ensure_seed()                    首次启动建默认租户+管理员
   ensure_default_menus()                   补齐每个租户的默认菜单
   ensure_default_alert_rules()
7. exports::recover_stale()                 逐租户回收 15 分钟前的未完成任务
8. 路由拼装                                内核路由 + /api/{plugin_id}
9. 中间件链（见 §3）
10. jobs::spawn()                           会话清理 + 审计告警
11. 前端静态托管（web_dist 存在时）
12. 审计分区补齐 + 6 个 24h 后台任务
```

**关键约束**：插件迁移失败 → 整体启动失败。这是刻意的：带着未知 schema 状态启动比不启动更危险。

### 2.3 启动期的隐性成本

| 操作 | 复杂度 | 影响 |
|---|---|---|
| `sync_plugin_menus` | 租户数 × 插件菜单数 | 1000 租户 × 20 菜单 = 2 万次 upsert |
| `ensure_default_menus` | 租户数 × 14 条 INSERT（`system_seed.rs` 实际 14 条） | 同上量级 |
| `ensure_default_alert_rules` | 租户数 | — |
| `recover_stale` | 租户数，**串行** | 每租户一个事务 |

**这些都在 `bind` 之前执行**，所以租户多时新实例启动会慢（滚动发布期间容量空窗）。
优化方向：改成后台任务 + `/readyz` 依赖一个 `startup_complete` 标记。

## 3. 请求生命周期

### 3.1 中间件链（从外到内）

`app.rs` 的 `.layer()` 是**后加在外层**，下表按请求进入顺序：

| # | 中间件 | 作用 | 失败时 |
|---|---|---|---|
| 1 | `security::headers` | CSP / X-Frame / Referrer / HSTS | — |
| 2 | `DefaultBodyLimit(2MB)` | 全局请求体上限 | 413 |
| 3 | `client_ip::inject` | 解析 `ClientMeta` 写入扩展 | — |
| 4 | `csrf::guard` | 不安全方法校验来源 | 403 |
| 5 | `CorsLayer` | 白名单 + credentials | 预检失败 |
| 6 | `CompressionLayer` | gzip，>1KB 文本 | — |
| 7 | `metrics::track` | 计数 + 延迟直方图 | — |
| 8 | `SetRequestId` / `Propagate` | 生成并回写 `x-request-id` | — |
| 9 | `TraceLayer` | 访问日志（INFO） | — |
| 10 | `CatchPanicLayer` | panic → 500 | 500 |
| 11 | `HandleError + LoadShed` | 过载 → 503 | 503 + Retry-After |
| 12 | `ConcurrencyLimit` | `max_concurrency` 信号量 | 触发 #11 |
| 13 | `TimeoutLayer` | 请求超时（只包 handler） | 408 |

**顺序踩坑记录**：

- `client_ip` 必须在限流/CSRF 之前，否则拿到未解析的伪造 IP；
- `security::headers` 在最外层，保证 403/503 也带 CSP；
- `ConcurrencyLimit` 必须在 `Timeout` 之外，否则排队时间被算进单请求超时。

### 3.2 Handler 的标准形状

```rust
async fn list_xxx(
    State(state): State<AppState>,        // 全局状态
    user: CurrentUser,                    // 认证（401）
    mut tx: TenantTx,                     // 租户事务 + RLS 上下文（须显式 commit）
    Query(q): Query<XxxQuery>,            // 查询参数
) -> Result<ApiResponse<Page<XxxVo>>, AppError> {
    require_perm(&user, PERM)?;           // 权限（403）
    let rows = sqlx::query_as(...)...;    // 数据权限条件内联在 SQL
    let total = ...;
    tx.commit().await?;                   // 漏写 = 回滚，改动不生效
    Ok(ApiResponse::new(Page { ... }))
}
```

**`TenantTx` 是提取器**：只要 handler 声明它，就自动 `BEGIN` + `set_config('app.tenant_id')`，
并在平台超管时额外设置 `app.platform='on'`。**忘记 `commit()` 会静默回滚**——
这是新人/AI 最容易犯的错，评审时必须逐条确认。

### 3.3 鉴权与数据权限是两套东西

| 层 | 位置 | 粒度 | 失败 |
|---|---|---|---|
| 认证 | `CurrentUser` 提取器 | 会话/PAT 是否有效 | 401 |
| 功能权限 | `require_perm()`（每个 handler **手写**） | 权限点字符串 | 403 |
| 数据权限 | SQL 里的 `scope` 条件 | 行 | 过滤掉（详情接口返回 404） |
| 行级兜底 | PostgreSQL RLS | 行 | 拦截 |

**注意**：功能权限没有路由级强制，靠每个 handler 自己调。
`system_identity::require_perm` 的注释里也写了「下一步会升级为路由层宏」。
新增接口忘记调 = 越权，`check-perms` 只校验常量存在性，**不校验是否被调用**。

## 4. 认证与会话

### 4.1 登录

```
POST /api/auth/login
  ├ ratelimit::login           每 IP 每分钟 60 次（进程内固定窗口）
  ├ client_ip::inject          可信代理解析
  ├ resolve_tenant()           显式租户码 / 唯一活跃租户
  ├ TenantTx::begin_tenant     注入 RLS 上下文
  ├ 查用户（不区分"不存在"）
  ├ 锁定检查                    锁定期内也做等价哈希（防时序）
  ├ verify_password_async      Argon2 在受控阻塞池
  ├ 失败：累加次数 → 可能锁定 → 写告警 → 提交 → 审计 → 401
  └ 成功：清计数 → 权限/数据范围 → 建会话 → Set-Cookie → 审计 → 200
```

**多处安全细节**（都有对应代码注释，改动前务必读）：

- 用户不存在 / 停用 / 锁定三个分支都调用 `burn_verification_time()` 对齐耗时；
- 密码校验失败也要 **commit**（失败计数必须落库）；
- 审计写在事务提交**之后**（避免记录未提交事件）；
- 令牌只存 SHA-256，Cookie 为 HttpOnly + SameSite=Lax，release 加 Secure。

### 4.2 会话存储

| 项 | 实现 |
|---|---|
| 表 | `sys.sys_session`，多实例共享 |
| 缓存 | 进程内 `RwLock`，TTL 30s，最多 10000 项 |
| 失效 | 写操作清本实例缓存并切换代次；注销前开始的查询不能重新填回旧会话 |
| 单端并发 | 事务级咨询锁按租户/用户串行执行删除与插入，失败整体回滚 |
| 多实例窗口 | 强制下线/改权限最长 30 秒后在其他实例生效 |
| 清理 | `jobs.rs` 每 10 分钟 `DELETE WHERE expires_at <= now()` |

### 4.3 个人 API Token

格式 `zc.{tenant_uuid}.{secret}`，存 SHA-256，支持 `scopes` 收窄。
**带 scopes 的 token 不算平台超管**（`is_super_admin()` 要求 `*`），这是刻意的：
避免一个只读令牌能改租户。

## 5. 多租户与数据权限

### 5.1 三层隔离

| 层 | 机制 | 覆盖范围 |


**未启用 RLS（7 张）**：

| 表 | 原因 |
|---|---|
| `sys_audit_log_202611` / `_202612` / `_202701` / `_default` | 审计按月分区。**分区子表不单独设 RLS**，访问统一经过父表 `sys_audit_log`（已 FORCE），策略由父表继承生效 |
| `sys_session` | 解析 token_hash 时尚无租户上下文；列表/撤销等管理操作显式按 tenant_id 过滤，不能视为受 RLS 保护 |
| `sys_tenant` | 平台级表，跨租户管理 |
| `sys_permission` | 全局字典（权限点由代码声明，所有租户共享） |

> **判定方法**（可随时复核，不依赖文档）：
> ```sql
> SELECT n.nspname, c.relname, c.relrowsecurity, c.relforcerowsecurity
> FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
> WHERE c.relkind='r' AND n.nspname IN ('sys','crm','demo') AND c.relname NOT LIKE '_sqlx%'
> ORDER BY 3,4,1,2;
> ```
> 这条查询只覆盖 sys/crm/demo；历史结果为 7 张 `(false,false)`。新增插件应扩展查询 schema 后核查例外表，
> 不能固定断言永远只有 7 张未启用表；**任何** `(true,false)` 都应核查是否遗漏 FORCE。

**迁移在哪一步 FORCE**：`0015_force_rls.sql`（11 张核心表）、`0022` / `0068` / `0069`（关联表与业务表）、
插件 `0004_force_rls.sql` / `0018`（CRM）、`demo/0002`。新增表必须在同一 PR 里补 FORCE 语句，
否则会重新引入「只 ENABLE」的缺口。

#### 这条约束有两道自动守护

| 层 | 手段 | 能发现什么 |
|---|---|---|
| 静态 | `scripts/check-rls-coverage.mjs`（`cargo xtask verify` 第 5 步 + CI） | 迁移里「建了策略但没有 FORCE」的表；反向也查「FORCE 了但没有策略」 |
| 运行期 | `apps/server/tests/rls_enforced.rs`（CI integration job） | 真实数据库上，**表 owner** 与**普通角色**两条路径都受策略约束 |

**为什么必须测两条路径**（这是最容易做假的测试）：

| 角色 | `ENABLE` 时 | `ENABLE + FORCE` 时 |
|---|---|---|
| 普通角色 | ✅ 被拦截 | ✅ 被拦截 |
| **表 owner** | ❌ **绕过** | ✅ 被拦截 |

只用普通角色测，`ENABLE`-only 的表也会「通过」——测试是假安全的。
生产环境的应用连接往往同时是建表角色（本仓库 `docker-compose.yml` 里
`zcadmin_app` 既是 database owner 又是建表角色），所以 **owner 路径才是真实路径**。

本地运行（需要两个角色，见测试文件头注释）：

```bash
export RLS_OWNER_DATABASE_URL="postgres://rls_owner:...@127.0.0.1:5432/zcadmin"  # 表 owner
export RLS_TEST_DATABASE_URL="postgres://rls_probe:...@127.0.0.1:5432/zcadmin"   # 普通角色
cargo test -p server --test rls_enforced -- --ignored --test-threads=1
```

测试会先断言「你给的角色确实是 owner 且不是超级用户」，用错角色会直接失败而不是假通过。

> **上线必须确认**：应用连接使用 `zcadmin_app`（`NOSUPERUSER NOBYPASSRLS`）。
> 若用超级用户连接，FORCE 也拦不住（超级用户永远绕过 RLS）；若用表 owner 连接，
> 只有 FORCE 能拦住。这是 `ops/init-app-role.sql` 存在的原因。
>
> **本地开发库注意**：本地手工建的库常常直接用超级用户或表 owner 连接，
> 这会让其他集成测试里的 RLS 断言失去意义（它们能过，只是因为超级用户绕过）。
> 只有 `rls_enforced.rs` 会校验连接角色的属性，跑它才是真正验证隔离。

### 5.3 数据范围（Data Scope）

登录时 `load_data_scope` 把多角色合并成一个逗号分隔字符串，存进会话：

| 角色配置 | 会话中的值 | SQL 含义 |
|---|---|---|
| 任一角色 `all` | `all` | 不过滤 |
| `dept_and_child` | `child,self` | 部门子树 ∪ 本人 |
| `dept` | `dept,self` | 本部门 ∪ 本人 |
| `custom` | `custom,self` | 自定义部门集合 ∪ 本人 |
| 无角色 | `self` | 仅本人（最小权限） |

**并集语义**：多角色取并集，不是取最大范围（除了 `all` 直接短路）。
`kernel::scope::condition()` 是唯一实现，接入 CRM 时通过 `scope_filter` 复用。

**`dept_id` 为空时**：`child` / `dept` 分支的 `dept_id = NULL` 永不匹配，等价于只看自己。
CI 有一条 grep 检查：文件里出现 `dept_and_child` 必须同时出现 `custom` 或调用 `kernel::scope::condition`。

### 5.4 越权返回 404

详情/删除等按 id 的接口，如果资源不在数据范围内，统一返回 **404 而不是 403**，
避免攻击者通过状态码探测资源是否存在。见 `api::ensure_customer_visible` 等函数。

## 6. 数据访问模式

### 6.1 没有 Repository 层（现状）

AGENTS 铁律 8 写着「所有查询必须经过 Repository」，但**当前代码里没有 Repository**：
SQL 直接写在 handler 或同模块的 `read.rs` 里（全仓库 462 处 `sqlx::query`）。

| 实际分层 | 说明 |
|---|---|
| `*_read.rs` / `*_types.rs` | CRM 插件里的读取与类型拆分（`contact_read.rs` 等） |
| handler 内联 SQL | kernel 的绝大多数模块 |
| `scope.rs` | 唯一被抽出来的 SQL 片段 |

**这是已知偏差**，不是文档遗漏。影响：

- 单测无法脱离数据库测业务规则；
- SQL 复用靠人眼，`scope` 已抽出但其他条件没有。

### 6.2 事务边界

| 模式 | 用法 | 例子 |
|---|---|---|
| 请求级事务 | `TenantTx` 提取器，handler 末尾 `commit()` | 几乎所有写接口 |
| 无用户上下文 | `TenantTx::begin_tenant` | 登录、PAT 解析 |
| 后台任务 | 手动 `pool.begin()` + `set_config` | 审计、租户清理 |
| 平台超管 | `TenantTx` 自动加 `app.platform='on'` | 租户账单/汇总 |

**跨插件事务是被禁止的**（AGENTS / 04 文档），实际也做到了：每个 handler 只写自己 schema。

### 6.3 连接池

`db::connect` 的关键设置（都在 `after_connect` 里下发到**每条连接**）：

```sql
SET statement_timeout = '5s'                                  -- 服务端强制终止
SET idle_in_transaction_session_timeout = '30s'                -- 防漏 commit
```

池参数：`max_connections=20`、`min_connections=5`、`acquire_timeout=5s`、
`max_lifetime=30min`、`idle_timeout=10min`。

**迁移例外**：`run_migrations` 会临时 `statement_timeout=0`，完成后恢复原值再还池。

## 7. 各子系统实现摘要

### 7.1 审计（最大子系统，17 个模块 / 3,624 行）

| 能力 | 模块 | 说明 |
|---|---|---|
| 写入 | `audit.rs` | 显式调用（非中间件），带 IP/UA；**失败只打日志** |
| 分区维护 | `audit_maintenance.rs` | 按月分区，启动补齐 2 个月，24h 检查 |
| 保留期 | 同上 | 按分区 `DROP`（比 DELETE 快且不膨胀） |
| 告警检测 | `audit.rs::detect_alerts` | 窗口内同 action 次数 ≥ 阈值 |
| Webhook | `audit_notify.rs` | HMAC-SHA256 签名 + 模板 + 指数退避（最多 8 次） |
| 订阅 | `audit_subscriptions.rs` + `dispatch` | 按用户订阅匹配写投递队列 |
| 死信 | `audit_deliveries.rs` | 列表、单条重试、批量重试 |
| 配置包 | `audit_config_*.rs` | 导入/导出/预览/快照/对比（6 个模块） |

**审计与业务不同事务**：审计写入失败不影响业务，代价是极端情况下丢审计。
强一致方案是 outbox 同事务写（文档里有设计，**未实现**）。

### 7.2 租户与计费（15 个模块 / 3,277 行）

```
租户生命周期：创建（带管理员）→ 状态（active/suspended）→ 软删 → 保留期 → 物理清理
配额：max_users / max_storage_bytes，超限返回 422
计费：usage_snapshot（日）→ 月末生成 draft 账单 → 收款/退款 → 逾期扫描 → 催收
```

**用量快照**由 24h 后台任务采集；**月末账单**任务只在每月 1 日执行（判断 `%d == "01"`）。

### 7.3 文件与导入导出

| 能力 | 限制 | 备注 |
|---|---|---|
| 上传 | 25MB（仅上传路由），全局 2MB | 落本地磁盘 `{tenant}/{uuid}` |
| 下载 | 全量读入内存 | 大文件不适合 |
| 文件删除 | 提交软删后再删物理内容 | 提交失败保留文件，物理删除失败记录运维清理信息 |
| 用户导入 | **500 行**（Argon2 成本） | 逐行 SAVEPOINT，部分成功 |
| CRM 导入 | `MAX_IMPORT_ROWS` | 与用户导入独立 |
| 异步导出 | 20000 行上限 | 内核与 CRM 插件全部走 `xlsx::run_anyhow` 受控阻塞池 |

**导出注册机制**：插件 `inventory::submit!` 注册 `ExportRegistration`，内核不认识具体类型。
**当前约束**：内核模板/错误报告/对账单及 CRM 同步导出全部先 `tx.commit()` 释放连接再通过 `xlsx::run` 生成；用户导入逐行 SAVEPOINT 隔离约束异常。

### 7.4 插件系统（支持编译期 + 运行期双层可插拔）

```rust
pub trait Plugin {
    fn meta(&self) -> PluginMeta;              // id/name/version/depends_on/order
    fn migrations(&self) -> Option<&'static Migrator>;
    fn routes(&self) -> Router<AppState>;      // 挂到 /api/{id}
    fn permissions(&self) -> Vec<PermissionDef>;
    fn menus(&self) -> Vec<MenuDef>;
    fn openapi(&self) -> Option<utoipa::openapi::OpenApi>;
}
```

| 事实 | 说明 |
|---|---|
| 注册 | `inventory::submit!`，编译期收集（当前含 `demo`、`crm`、`workflow`） |
| 编译期可插拔 | `apps/server/Cargo.toml` 定义 `plugin-demo` / `plugin-crm` / `plugin-workflow` feature，可按系统需求裁剪二进制 |
| 运行期可插拔 | `config/default.toml` 的 `[plugins] disabled = [...]` 或环境变量 `DISABLED_PLUGINS` 动态跳过指定插件的迁移、权限、菜单与路由 |
| 排序 | 先按 `(order, id)` 稳定排序，再 DFS 拓扑排序 + 环检测 |
| 契约缺失 | `on_start` / 事件总线 **尚未实现** |

### 7.5 可观测

| 类型 | 实现 |
|---|---|
| 指标 | `http_requests_total`、`http_request_duration_seconds`、`db_pool_connections`、`db_pool_idle`、`db_pool_saturated`、会话缓存三件套 |

## 10. 验证方式

```bash
# 全量（提交前必须全绿）
cargo xtask verify            # 六步：fmt + clippy + 普通测试 + 架构 + RLS 静态 + 权限/错误码

# 分项
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace                       # 执行普通测试，真库 ignored 用例另跑
cargo xtask arch-check                       # kernel 不依赖插件、插件互不引用
cargo xtask check-perms                      # 权限 4 项 + 错误码 1 项
cargo xtask openapi                          # 导出 contracts/openapi.json
```

HTTP 契约测试和 security_baseline 的 panic 用例不需要真库；需真库的用例标记为 ignored，应显式运行：

```bash
export DATABASE_URL="postgres://zcadmin:zcadmin@127.0.0.1:5432/zcadmin"
cargo test -p server --test smoke -- --ignored --test-threads=1
cargo test -p server --test security_baseline -- --ignored --test-threads=1
cargo test -p kernel --test session_atomicity --test file_atomicity --test user_import_atomicity -- --ignored --test-threads=1
# 其余见 .github/workflows/ci.yml 的 integration job
```

| 测试文件 | 覆盖 | 需要库 |
|---|---|---|
| `smoke.rs` | 全链路（3,755 行） | ✅ |
| `security_baseline.rs` | IP 伪造、panic 隔离、503、指标鉴权、连接超时 | 部分 |
| `rbac_matrix.rs` / `rbac_role.rs` | 权限矩阵 | ✅ |
| `scope_matrix.rs` / `custom_scope.rs` | 五种数据范围 | ✅ |
| `tenant_isolation.rs` | 租户管理员≠平台超管 | ✅ |
| `single_session.rs` | 单端登录 + 强制下线 | ✅ |
| `export_maintenance.rs` | 陈旧任务回收 | ✅ |
| `csrf_guard.rs` | 来源校验 | ✅ |
| `webhook_*.rs` | 投递与重试 | 部分需回环 TCP |
| `rls_enforced.rs` | **RLS 真实隔离**：owner 路径 + 普通角色路径 + 分区继承 | 需专用非超级用户角色 |
| `bench.rs` | 性能基线（25 并发） | ✅ |

`cargo xtask verify` 不运行前端构建和契约重新生成；还需按改动执行 `cargo xtask openapi`，
以及 frontend 下 `npm run gen:api`、`npm test`、`npm run build`。RLS 静态检查不代替上表的 `rls_enforced` 真库角色验证。

**Windows 本地注意**：需要 MinGW 在 `PATH` 里（`ring` 等 crate 要 C 编译器），
否则 `cargo check` 会报 `failed to find tool "gcc.exe"`。

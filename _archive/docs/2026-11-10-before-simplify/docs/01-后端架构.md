## 1. 进程模型与运行时

### 1.1 线程模型

```
main
 ├── tokio::main(multi_thread, worker_threads = CPU 核数)
 │    ├── HTTP accept 循环（axum::serve + graceful_shutdown + 停机 watchdog）
 │    ├── 后台周期任务（tokio::spawn + interval，多实例幂等）
 │    │    ├── 会话清理 10min / 审计告警 5min
 │    │    └── 审计分区、租户清理、用量快照、账单扫描 24h
 │    └── 指标/健康检查辅助任务
 └── 受控 blocking 池（默认并发 4，见 crates/kernel/src/blocking.rs）
      └── 仅用于：Argon2、Excel 解析/生成、同步文件 IO
```

> **现状说明**：outbox 派发器与任务调度器（`sys_job`）在设计里，但当前未实现。
> 后台任务目前是纯 `tokio::spawn` + `interval`（见 `crates/kernel/src/app.rs` 与 `jobs.rs`），
> 依赖"每个任务自身幂等"来支持多实例。

**规则**：

- 任何单次 > 1ms 的 CPU 或阻塞 IO 必须走 [`kernel::blocking::run`]，否则会阻塞整个 worker。
- **不能直接用 `spawn_blocking` 处理 Argon2**：tokio 阻塞池默认上限 512，
  单次 Argon2 约 19 MiB，并发一高就是「512 × 19 MiB」的内存峰值。
  必须经过信号量限流（`BLOCKING_MAX_CONCURRENCY`，默认 4），排队超时返回 503。
- 禁止在 handler 里 `std::thread::sleep`、`block_on`、同步文件读写。
- 计算密集（报表导出、Word 生成）走**任务队列**，不占请求线程。

### 1.2 优雅停机

```rust
// 关键：axum 的 graceful shutdown 自身没有超时上限。
// 必须用 watchdog 兜底，否则一个卡死的请求会让进程永远不退出。
let (tx, rx) = tokio::sync::oneshot::channel();
let server = axum::serve(listener, router.into_make_service_with_connect_info::<SocketAddr>())
    .with_graceful_shutdown(async move {
        let _ = rx.await;
        state.begin_shutdown();          // /readyz 立即 503，先摘流
        tokio::time::sleep(DRAIN_GRACE).await;
    });
tokio::select! {
    biased;
    result = server => result,
    _ = watchdog(grace, tx) => { /* 超时：放弃剩余请求 */ }
}
// 顺序：SIGTERM → 置 not-ready → 摘流缓冲 3s → 停止接收新请求
//      → 等待 in-flight（上限 shutdown_grace_secs，默认 20s）
//      → 关闭连接池 → flush OTel → 退出
```

**验收**：发布时 `kubectl rollout` / `docker stop` 不产生 5xx，不丢 in-flight 事务。
`docker-compose.yml` 的 `stop_grace_period` 必须大于 `shutdown_grace_secs + 3s`（当前 40s）。

### 1.3 超时预算（全链路）

| 层级 | 超时 | 说明 |
|---|---|---|
| Nginx / Ingress | 60s | 兜底 |
| 请求总超时（`TimeoutLayer`） | 30s（`request_timeout_secs`） | 只包 handler，不含响应体传输 |
| 单条 SQL（`statement_timeout`） | 5s（`statement_timeout_secs`） | 启动期校验必须严格小于上一层 |
| 外部 HTTP 调用 | 3s 连接 + 10s 总 | 必须有超时与重试上限 |
| 连接池获取 | 5s（`acquire_timeout_secs`），超时返回 503 | 避免雪崩排队 |
| 事务空闲（`idle_in_transaction_session_timeout`） | max(30s, SQL 超时×6) | 防止漏 commit 长期占锁 |
| Argon2 阻塞池排队 | 3s，超时返回 503 | 见 `kernel::blocking` |
| 优雅停机 drain | 20s（`shutdown_grace_secs`） | 另加 3s 摘流缓冲 |

> 预算必须**逐层递减**：上游 30s > 业务 25s > SQL 5s。任何一层缺失超时，都会在故障时变成线程堆叠。

## 3. 请求生命周期

### 3.1 中间件顺序（顺序即语义，不可随意调整）

> 实现见 `crates/kernel/src/app.rs` 第 6 步。下表按**请求进入顺序**（从最外层到最内层）排列；
> axum 的 `.layer()` 语义是「后加的在外层」，与直觉相反，改代码时务必对照。

| # | 中间件 | 作用 | 为什么在这个位置 |
|---|---|---|---|
| 1 | `SecurityHeaders` | CSP、X-Frame-Options、HSTS | 最外层：被 CSRF/限流拒绝的 4xx 也要带头 |
| 2 | `DefaultBodyLimit(2MB)` | 默认请求体上限 | 在解析 body 之前拒绝超大请求 |
| 3 | `ClientIp` | 可信代理 + 真实 IP 解析 → `ClientMeta` | 限流、审计、日志都依赖它 |
| 4 | `CsrfLayer` | 校验不安全方法的来源 | 在认证前，省一次会话查询 |
| 5 | `CorsLayer` | 仅 API 域名白名单 | 预检请求不应进入鉴权链 |
| 6 | `CompressionLayer` | gzip（>1KB 的文本响应） | 在 body 生成之后、写回之前 |
| 7 | `Metrics` | `http_requests_total` / 延迟直方图 | 覆盖后续所有失败 |
| 8 | `SetRequestId` / `PropagateRequestId` | 生成并回写 request-id | 后续日志与响应头都能用上 |
| 9 | `TraceLayer` | 访问日志与耗时（INFO 级） | 包住业务与过载保护 |
| 10 | `CatchPanicLayer` | panic → 500，进程存活 | 必须配合 `panic = "unwind"` |
| 11 | `HandleError + LoadShed` | 过载时立即 503 | 在超时之外：先拒绝，再谈单个请求超时 |
| 12 | `ConcurrencyLimit` | 并发上限（`max_concurrency`） | 保护进程与连接池 |
| 13 | `TimeoutLayer` | 请求总超时（只包 handler future） | 最内层，避免把排队算进上游 |

> **常见错误**：把 `TimeoutLayer` 放最外层，导致超时后仍继续处理；把 `Compression` 放认证前，预检响应被压缩出错；把 `ClientIp` 放在 `Csrf`/限流之后，导致拿到的是未解析的伪造 IP。
> `TimeoutLayer` **不约束响应体传输**，大文件下载/慢客户端需要网关层兜底。

### 3.1.1 客户端 IP 与可信代理

| 场景 | 行为 |
|---|---|
| `trusted_proxies` 为空（默认） | 只认 TCP 对端地址，`X-Forwarded-For` 一律忽略 |
| 对端在可信网段内 | 从右往左扫描 XFF，取第一个不可信地址（标准语义） |
| 拿不到对端地址（`oneshot` / 嵌入式） | 退化为 XFF 第一段，**仅测试路径会走到** |

生产入口必须使用 `into_make_service_with_connect_info::<SocketAddr>()`，否则可信代理判断失效。
登录限流、登录审计、`audit_log.ip` 全部走同一个解析结果，不允许各自读请求头。

### 3.2 提取器（Extractor）约定

```rust
// 统一入口：一次解析，处处可用
pub struct Ctx {
    pub principal: Principal,      // 用户 + 角色 + 权限位图
    pub tenant: TenantCtx,         // 租户 id + 时区 + 语言 + 配额
    pub trace_id: TraceId,
    pub db: PgPool,
}

#[async_trait]
impl FromRequestParts<AppState> for Ctx { /* ... */ }

// handler 签名统一为：
async fn list_customers(
    State(st): State<AppState>,
    ctx: Ctx,                          // 认证 + 租户 + 追踪
    Query(q): Query<CustomerQuery>,     // 查询参数（含分页/排序）

```

**反模式**：handler 里到处 `Extension<Principal>`、`HeaderMap` 手动取 token —— 不可测试且易漏。

## 4. 分层规范

### 4.1 职责边界

| 层 | 职责 | 允许 | 禁止 |
|---|---|---|---|
| `api/`（handler） | HTTP 语义：解析、校验、调用 service、组装响应 | DTO ↔ 领域对象转换、权限注解 | 写 SQL、开事务、业务分支 |
| `service/` | 业务规则、事务边界、领域事件、跨 repo 编排 | 调用多个 repo、发事件、调外部服务 | 感知 HTTP（Header/Cookie/StatusCode） |
| `repo/` | SQL、映射、分页查询 | sqlx、sea-query 条件组合 | 业务判断、发事件、跨插件写 |
| `domain/` | 实体、值对象、状态机、领域错误 | 纯逻辑、无 IO | 依赖 sqlx/axum |

```rust
// service 的事务边界：显式传入 &mut Tx，不隐式开事务
impl CustomerService {
    pub async fn create(&self, ctx: &Ctx, cmd: CreateCustomer) -> Result<Customer> {
        let mut tx = self.db.begin().await?;                    // 边界在此
        let c = Customer::new(cmd, ctx.principal.id)?;          // 领域校验
        repo::customer::insert(&mut tx, &c).await?;
        outbox::publish(&mut tx, CustomerCreated { id: c.id }).await?;
        tx.commit().await?;
        Ok(c)
    }
}
```

### 4.2 三条硬规则

1. **一个请求 = 一个事务**（读多表时用 `REPEATABLE READ` 可选），禁止在循环里开事务。
2. **跨聚合一致性用事件**，不用分布式事务；同聚合内用单事务。
3. **DTO 与实体分离**：`CreateXxxReq` / `UpdateXxxReq` / `XxxVo` 三套，禁止把实体直接序列化给前端（防字段泄漏 + 防 mass assignment）。

### 4.3 分层代码量参考

| 层 | 单接口行数 | 说明 |
|---|---|---|
| handler | 5–30 行 | 超过 40 行说明业务漏到 API 层 |
| service | 20–120 行 | 超过 200 行拆分用例 |
| repo | 10–80 行 | 复杂查询可用 `sea-query` 组合 |

## 5. 事务与并发

### 5.1 事务规范

| 场景 | 隔离级别 | 说明 |
|---|---|---|
| 默认 | READ COMMITTED | PG 默认，够用且开销小 |
| 统计对账 | REPEATABLE READ | 同一快照多次读 |
| 严格唯一性 | SERIALIZABLE + 重试 | 仅关键场景，需实现 40001 重试 |

```rust
// 死锁/序列化失败统一重试封装
pub async fn with_retry<F, T>(mut f: F) -> Result<T>
where F: FnMut() -> BoxFuture<'_, Result<T>> {
    for attempt in 0..3 {
        match f().await {
            Err(e) if e.is_retryable() && attempt < 2 => {
                tokio::time::sleep(Duration::from_millis(20 << attempt)).await;
            }
            r => return r,
        }
    }
    unreachable!()
}
```

**重试幂等前提**：被重试的闭包必须整体可重放（不要在闭包外做副作用）。

### 5.2 并发控制

| 手段 | 场景 | 实现 |
|---|---|---|
| 乐观锁 | 表单编辑冲突 | `version` 列 + `WHERE version = $n`，影响 0 行 → 409 |
| 悲观锁 | 库存扣减、序号生成 | `SELECT ... FOR UPDATE`（短事务！） |
| 唯一约束 | 防重复提交 | 业务唯一键 + 捕获 23505 → 409 |
| 幂等键 | 支付/下单/外部回调 | `sys_idempotency(key, resource, response, expires_at)` |
| 分布式锁 | 跨实例互斥 | PG `pg_try_advisory_lock`（优先）或 Redis SETNX |
| 队列表 | 任务分发 | `FOR UPDATE SKIP LOCKED` |

```sql
-- 任务队列标准写法：多实例安全，无锁竞争
WITH picked AS (
  SELECT id FROM sys_job_queue
   WHERE status = 'pending' AND run_at <= now()
   ORDER BY run_at
   LIMIT 10
   FOR UPDATE SKIP LOCKED
)
UPDATE sys_job_queue q SET status = 'running', worker = $1, started_at = now()
  FROM picked WHERE q.id = picked.id
RETURNING q.*;
```

### 5.3 幂等设计（写接口三件套）

```
1. 客户端生成 Idempotency-Key（UUID），随请求发送
2. 服务端 INSERT ... ON CONFLICT DO NOTHING 抢占
   ├ 抢到 → 执行业务 → 回写响应快照
   └ 没抢到 → 读已有记录：completed 返回快照；processing 返回 409 + Retry-After
3. 记录 TTL 24h（可按业务延长），由清理任务回收
```

**必须幂等的接口**：创建订单、支付回调、审批提交、批量导入、外部 Webhook。

## 6. 错误模型

### 6.1 分层错误

```rust
// 领域错误：只描述业务语义，不含 HTTP
#[derive(Debug, thiserror::Error)]
pub enum CustomerError {
    #[error("客户名称已存在")] Duplicated,
    #[error("客户不存在")] NotFound,
    #[error("客户已被引用，无法删除")] InUse,
}

// 应用错误：唯一对外出口
pub enum AppError {
    Domain(Box<dyn DomainError>),   // 4xx，带业务码
    Validation(ValidationErrors),   // 422
    Unauthorized,                   // 401
    Forbidden,                      // 403
    NotFound,                       // 404
    Conflict,                       // 409
    RateLimited { retry_after: u64 },// 429
    Unavailable,                    // 503，过载/停机，带 Retry-After
    Internal(anyhow::Error),        // 500，日志打全栈，响应只给 trace_id
}
```

> 实现与上表略有差异：当前 `RateLimited` 不带字段，`Retry-After` 由 `IntoResponse`
> 统一注入固定 5 秒（见 `crates/kernel/src/error.rs`）。

### 6.2 响应格式（RFC 9457 problem+json）

```json
{
  "type": "https://errors.example.com/crm.customer.duplicated",
  "title": "客户名称已存在",
  "status": 409,
  "code": "crm.customer.duplicated",
  "detail": "名称「XX 科技」已被占用",
  "traceId": "0192f3a1-...",
  "errors": [{ "field": "name", "message": "已存在" }]
}
```

**错误码规范**：`{plugin}.{domain}.{reason}`，全小写点分。**一经发布不可变更语义**，只能新增。错误码总表由 `xtask openapi` 汇总生成，前端据此维护文案。

**429 / 503 必须带 `Retry-After`**（通用错误为 5 秒，登录固定窗口限流为 60 秒）。没有这个头，客户端通常
会立刻重试，把过载放大成雪崩。两者语义区分：

| 状态 | 含义 | 客户端应做什么 | 编排系统应做什么 |
|---|---|---|---|
| 429 | 你的请求太频繁 | 退避后重试 | 不处理 |
| 503 | 本实例暂时没有余量（并发满 / 阻塞池排队 / 数据库不可用 / 正在停机） | 退避，可换实例重试 | 停止向该实例转发 |

`AppError` 统一使用 `application/problem+json`；连接池获取超时/关闭映射为 503，
真实 SQL 执行错误仍为 500，内部错误不向调用方回显。分页 `OFFSET` 对超大页码饱和到
`i64::MAX`，避免 u64 乘法溢出或转成负偏移量。

### 6.3 五条铁律

1. `anyhow` 不得出现在 handler 返回值；只在启动期与后台任务内部使用。
2. 500 响应**绝不**包含 SQL、路径、堆栈；只给 `traceId`。
3. 每个 4xx 必须可被用户理解（运营能看懂），技术细节进日志。
4. 校验错误一次性返回**全部**字段错误，不要逐条抛。
5. 错误码变更走评审，前端有对应映射，否则用户看到 "unknown error"。

## 7. 校验与入参安全

| 风险 | 防护 |
|---|---|
| Mass assignment（前端传 `is_super: true`） | DTO 显式字段 + `#[serde(deny_unknown_fields)]` |
| 超长字符串 / 大 body | `DefaultBodyLimit::max(2MB)`，字段级 `length` 校验 |
| 非法枚举 | Rust enum + serde 反序列化即拒绝 |
| 分页炸弹（pageSize=100000） | 服务端硬上限 200，超出即 422 |
| 排序注入（`order by` 拼接） | 排序列白名单枚举，只允许映射到固定列 |
| 富文本 XSS | 后端 sanitize（`ammonia`），前端渲染白名单 |
| 文件上传 | 类型白名单 + 大小限制 + 魔数校验 + 存储隔离域 |

```rust
#[derive(Deserialize, Validate)]
#[serde(deny_unknown_fields)]
pub struct CreateCustomerReq {
    #[validate(length(min = 2, max = 64))]
    pub name: String,
    #[validate(email)]
    pub email: Option<String>,
    #[validate(range(min = 0, max = 100_000_000))]
    pub credit_limit: Option<i64>,
}
```

## 8. API 契约规范

### 8.1 基础约定

| 项 | 规范 |
|---|---|
| 前缀 | `/api/{plugin}/{resource}`，全局版本 `/api/v1/...`（仅在不兼容变更时升版） |
| 方法 | GET 查询、POST 创建、PUT 全量更新、PATCH 局部、DELETE 删除 |
| 命名 | 资源复数、kebab-case：`/api/crm/customer-groups` |
| 时间 | 一律 RFC 3339 UTC（`2026-10-28T08:00:00Z`），前端按租户时区展示 |
| ID | UUIDv7 字符串，路径参数不做自增 |
| 金额 | 字符串传输（避免 JS 精度丢失），后端 `Decimal` |
| 空值 | 未设置用 `null`，不省略字段（前端类型稳定） |
| 枚举 | 传输字符串码值，前端字典翻译 |

### 8.2 统一响应包

```json
// 成功
{ "data": {...}, "traceId": "..." }
// 分页
{ "data": [...], "page": { "page": 1, "size": 20, "total": 135, "hasNext": true }, "traceId": "..." }
```

> 不套 `{code:0,msg:"ok"}` 这种业务码外壳——HTTP 状态码已经表达成功/失败，业务码放 problem+json 的 `code`。**双轨制（HTTP 200 + 业务 code）是历史包袱，不要继承。**

### 8.3 分页

| 场景 | 方式 | 说明 |
|---|---|---|
| 后台列表（有总数） | Offset：`?page=1&size=20` | `total` 用 `count(*) over()` 或独立 count，> 10 万行改估算 |
| 大数据/无限滚动 | Cursor：`?cursor=xxx&size=50` | 游标 = `(created_at, id)`，稳定且快 |
| 导出 | 异步任务 + 分批游标 | 禁止同步导出 10 万行 |

```sql
-- count 优化：大表用估算，避免全表扫描
SELECT reltuples::bigint FROM pg_class WHERE relname = 'customer';
```

### 8.4 过滤与排序 DSL

```
GET /api/crm/customers?filter[name.ct]=科技&filter[status.in]=active,trial&sort=-createdAt&page=1&size=20
```

- 白名单字段 + 操作符（`eq/ne/ct/in/gt/lt/between/isNull`），非法字段直接 422。
- 排序仅允许白名单列，`-` 前缀表示倒序。
- 复杂报表查询走独立 `POST /search`（body 传条件），避免 URL 超长。

### 8.5 长任务与异步接口

```
POST /api/report/export  → 202 Accepted
{ "jobId": "...", "pollUrl": "/api/system/jobs/{id}" }

GET /api/system/jobs/{id} → { "status": "running", "progress": 42 }
GET /api/system/jobs/{id}/result → 302 到预签名下载 URL（有效期 10 分钟）
```

## 9. 认证与会话

### 9.1 登录流程

```
POST /api/auth/login {username, password, tenant?}
 ├ 限流：同 IP LOGIN_RATE_LIMIT_PER_MIN（默认 60）/分钟，进程内固定窗口
 ├ 解析客户端 IP：TCP 对端 + trusted_proxies（见 §3.1.1）
 ├ 账号锁定：连续 max_failed_attempts（默认 5）次失败锁 lock_seconds（默认 900s）
 ├ 校验 argon2id（m=19456, t=2, p=1），在受控阻塞池中执行
 │   └ 用户不存在/停用/锁定 也做等价哈希，防时序枚举
 ├ 建会话：sys.sys_session（令牌只存 SHA-256 摘要）
 ├ 下发 Cookie：
 │   zcadmin_token  HttpOnly; SameSite=Lax; Path=/; Max-Age=session_ttl_secs
 │                  release 构建额外加 Secure（必须部署在 HTTPS 之后）
 └ 返回：用户信息 + 权限点集合 + mustChangePassword
```

> 目标设计中的 access/refresh 双令牌、MFA、验证码**均未实现**；
> 当前是单一会话 Cookie（默认 8 小时），刷新靠重新登录。
```

### 9.2 会话与刷新

**当前实现**（`crates/kernel/src/session.rs`）：

| 项 | 实现 |
|---|---|
| 令牌 | 随机 UUID，Cookie 中明文传输，DB 只存 SHA-256 摘要 |
| 存储 | PostgreSQL `sys.sys_session`，多实例共享 |
| 进程内缓存 | 30 秒 TTL，上限 10000 项；代次校验阻止失效前的旧查询回填；**写操作只清本实例** |
| 主动踢人 | 删除会话行 + 清本实例缓存；多实例有最长 30 秒窗口 |
| 并发登录 | `auth.single_session` / `AUTH_SINGLE_SESSION`；true 时以账号事务锁串行替换，插入失败回滚旧会话删除 |
| 过期 | `auth.session_ttl_secs`，默认 8 小时；无滑动续期、无空闲超时 |
| 强制改密 | `must_change_password` 期间只放行 `/change-password`、`/me`、`/logout` |
| 密码策略 | 租户级 `sys_password_policy`：长度/字符类/历史次数/有效期 |
| 个人 API Token | `sys.sys_api_token`，`zc.{tenant}.{secret}`，支持 scope 收窄 |

退出登录必须确认数据库撤销成功后再返回 204 和过期 Cookie；存储不可用返回 503，
前端保留页面并提示重试。退出/重新登录同时清理用户权限、vue-query 和字典缓存；
旧的 `/me` 请求不能恢复已清除的身份，字典查询传递取消信号以阻止旧数据回填。

**目标设计（未实现）**：

| 项 | 目标 |
|---|---|
| Access / Refresh | JWT 15 分钟 + 一次性轮换 Refresh 7 天 |
| 空闲超时 | 30 分钟无操作自动失效 |
| MFA | TOTP，管理员强制 |
| 敏感操作二次认证 | `sudo` 短期票据（5 分钟） |

### 9.3 CSRF 防护

**当前实现（2026-11）**：不使用双提交 token，改为**来源校验**（`crates/kernel/src/csrf.rs`）：

```
对 POST/PUT/PATCH/DELETE：
  Sec-Fetch-Site: cross-site        → 403
  Origin 存在且与 Host 不同源        → 403
  无 Origin（curl/服务端/测试）      → 放行，由认证与权限点负责
豁免：GET/HEAD/OPTIONS
```

配合会话 Cookie 的 `SameSite=Lax`，覆盖跨站表单提交与跨站 fetch。

**目标设计（未实现，勿照抄）**：

```
前端：从 cookie 读 csrf_token → 请求头 X-CSRF-Token
后端：常量时间比较 header 与 cookie；不一致 → 403
```

若将来启用双提交（例如 `SameSite` 被迫改为 `None` 时），必须同时：
下发非 HttpOnly 的 `csrf_token`、前端拦截器注入头、后端做常量时间比较，
并保留现有的 Origin/Sec-Fetch-Site 校验作为第二层。

## 10. 授权

### 10.1 三层模型

| 层 | 粒度 | 实现 |
|---|---|---|
| 功能权限（RBAC） | 接口 / 按钮 | 权限点 `crm:customer:add`，路由级 `require_perm!` |
| 数据权限 | 行 | `DataScope` → SQL 条件注入 |
| 字段权限 | 列 | 序列化时按角色脱敏（手机号 `138****1234`） |

```rust
// 路由级：编译期检查权限点是否在插件声明中存在（xtask 校验）
Router::new()
    .route("/customers", get(list).post(create))
    .route_layer(require_perm!("crm:customer:list"))
```

### 10.2 对象级授权（防 IDOR）

**这是管理后台最常见的漏洞**：`GET /api/crm/customers/{id}` 只校验了"有查询权限"，没校验"这条数据属于我"。

```rust
// 统一入口：所有按 id 取单条的 repo 方法必须带 scope
let customer = repo::customer::get_scoped(&mut tx, id, &ctx.scope()).await?
    .ok_or(AppError::NotFound)?;   // 越权一律返回 404，不返回 403（不泄漏存在性）
```

**规范**：`get_by_id` 这类方法**不提供无 scope 版本**，从类型上杜绝漏用。

### 10.3 权限点治理

- 命名：`{plugin}:{resource}:{action}`，action 限 `list/get/add/edit/delete/export/import/audit`。
- 插件启动时 `upsert` 到 `sys_permission`，**不删除**已消失的权限点（标记 `deprecated`），避免角色配置丢失。
- 权限点总数上限建议 ≤ 5000，前端一次拉全量位图（bitset），鉴权 O(1)。

## 11. 多租户运行时

### 11.1 租户解析顺序

```
1. JWT claim `tid`（登录时选定）
2. 请求头 `X-Tenant-Id`（仅超级管理员"切换租户"场景，需校验授权）
3. 子域名 `acme.example.com`（SaaS 对外）
4. 默认租户（单租户私有化部署）
→ 冲突时以 1 为准，并记审计
```

### 11.2 上下文注入

```rust
// 每个请求一个事务，SET LOCAL 随事务结束自动失效（不会污染连接池）
let mut tx = pool.begin().await?;
sqlx::query("SELECT set_config('app.tenant_id', $1, true), set_config('app.user_id', $2, true)")
    .bind(ctx.tenant.id.to_string())
    .bind(ctx.principal.id.to_string())
    .execute(&mut *tx).await?;
```

**必须 `true`**（local），写 `false` 会污染连接，造成跨租户数据泄漏 —— 这是 P0 级事故源。

### 11.3 租户配额与限流

| 维度 | 手段 |
|---|---|
| 请求量 | 令牌桶按 `tenant_id` 分桶，超限 429 |
| 存储量 | 定时统计 `pg_total_relation_size` 按 schema/租户汇总，超限告警 |
| 用户数 | 创建用户时校验 `sys_tenant.max_users` |
| 并发任务 | 每租户队列权重，防单租户占满 worker |

## 12. 缓存

### 12.1 分层与失效

| 层 | 内容 | TTL | 失效 |
|---|---|---|---|
| L1 本地（moka） | 字典、参数、权限位图、菜单树 | 60s | 版本号轮询（DB `sys_config_version`） |
| L2 Redis | 会话、验证码、限流计数、热点列表 | 5–30min | 主动删除 + 短 TTL 兜底 |
| DB | 唯一真相 | — | — |

```rust
// 缓存键规范：{env}:{tenant}:{plugin}:{entity}:{id}:v{schema_version}
// 版本号进 key，天然支持整体失效（改字典 → 版本 +1）
format!("{env}:{tid}:sys:dict:{code}:v{ver}")
```

### 12.2 三大故障防护

| 问题 | 方案 |
|---|---|
| 击穿（热点 key 过期） | 单飞（singleflight）+ 逻辑过期 |
| 雪崩（同时过期） | TTL 加 ±10% 随机抖动 |
| 穿透（查不存在的 id） | 空值缓存 60s + 布隆过滤器（可选） |

**一致性原则**：**先更新 DB，再删缓存**（不是更新缓存）；删除失败则发消息重试。绝不接受"缓存与 DB 双写"。

## 13. 领域事件与 Outbox

### 13.1 表结构

```sql
CREATE TABLE sys.outbox (
  id            uuid PRIMARY KEY,
  tenant_id     uuid NOT NULL,
  aggregate     text NOT NULL,          -- 'crm.customer'
  aggregate_id  uuid NOT NULL,
  event_type    text NOT NULL,          -- 'crm.customer.created'
  payload       jsonb NOT NULL,
  headers       jsonb NOT NULL DEFAULT '{}',
  status        text NOT NULL DEFAULT 'pending',  -- pending|processing|done|dead
  attempts      int  NOT NULL DEFAULT 0,
  available_at  timestamptz NOT NULL DEFAULT now(),
  created_at    timestamptz NOT NULL DEFAULT now(),
  processed_at  timestamptz
);
CREATE INDEX ON sys.outbox (status, available_at) WHERE status IN ('pending','processing');
```

### 13.2 派发器

```
loop (每 200ms 或 LISTEN/NOTIFY 唤醒):
  BEGIN;
  SELECT ... WHERE status='pending' AND available_at <= now()
    ORDER BY created_at LIMIT 100 FOR UPDATE SKIP LOCKED;
  → 逐条投递给订阅者（进程内）/ 标记 processing
  COMMIT;
  成功 → done；失败 → attempts+1，指数退避（1s,5s,30s,5m...）
  attempts > 10 → dead + 告警
```

### 13.3 语义与约束

| 项 | 说明 |
|---|---|
| 投递语义 | **至少一次**，消费者必须幂等（按 `event_id` 去重表） |
| 顺序 | 同一 `aggregate_id` 保序（单条队列 + 串行消费），跨聚合不保证 |
| 事务性 | 事件与业务同事务写入，`COMMIT` 后必然可派发 |
| 延迟 | 通常 < 1s；高峰可接受 5s |
| 消费者 | 必须设置超时，禁止长事务；失败不阻塞其他事件 |

## 14. 任务调度

| 类型 | 触发 | 实现 |
|---|---|---|
| Cron 定时 | 表达式 | `sys_job` 表 + 调度器每 30s 扫描，advisory lock 选主 |
| 一次性延迟 | `run_at` | `sys_job_queue` + SKIP LOCKED |
| 手动触发 | API | 写队列，立即执行，返回 jobId |
| 重试 | 失败 | 指数退避，最大 10 次，进死信表 |

```sql
-- 选主：多实例只有一个调度器在跑
SELECT pg_try_advisory_lock(hashtext('sys.job.scheduler'));
```

> **M3 现状**：先用 `tokio interval` 实现会话清理这类幂等任务（`kernel/src/jobs.rs`）；
> 出现「需要持久化、重试、手动触发」的任务时再切到 apalis，接口不变。

**任务规范**：

- 每个任务必须**幂等**且**可中断**（检查 `ctx.is_cancelled()`）。
- 必须记录 `sys_job_log`（开始/结束/耗时/结果/异常摘要）。
- 长任务必须上报进度（`update_progress(job_id, pct)`）。
- 禁止在任务里做无限循环；必须有超时（默认 30 分钟）。

## 15. 文件与导入导出

### 15.1 上传（预签名直传，后端不经手字节）

```
1. 前端 POST /api/system/files/presign {name, size, mime, sha256}
2. 后端校验：类型白名单、大小上限、租户配额 → 生成对象键
   key = {tenant}/{plugin}/{yyyy}/{mm}/{uuid}.{ext}
3. 返回预签名 PUT URL（10 分钟）+ fileId
4. 前端直传 MinIO/S3（支持分片、断点续传）
5. 前端 POST /api/system/files/{id}/complete → 后端 HEAD 校验大小/类型 → 落库
6. 异步钩子：病毒扫描、图片压缩、文档预览转换
```

**禁止**：把文件字节流经 axum 中转（内存与带宽双杀）。

### 15.2 下载

- 私有文件一律**预签名 GET**（10 分钟），后端只做鉴权与签名。
- 大文件支持 `Range`；下载行为记审计（谁、何时、哪个文件）。

### 15.3 导入（Excel/CSV）

```
上传 → 解析（kernel::blocking::run，限流）→ 校验（逐行）→ 临时表 staging
  → 批量 UPSERT（COPY 到临时表再 MERGE，10 万行 < 5s）
  → 生成错误报告（行号 + 原因）→ 通知
```

**规范**：单次导入上限 5 万行（超出拆分）；全量失败回滚，部分成功需明确策略（默认全有或全无）。

> **现状差异（必须知道）**：当前用户导入上限是 **500 行**，因为每行都要做一次 Argon2
> （约 40~60ms），5 万行 = 约 50 分钟。真正的大批量导入必须改成"异步任务 + 分批"
> （见 §15.4 的导出模式），不能只把常量改大。
> 解析走 `kernel::blocking::run`（受控阻塞池，默认并发 4），不要直接 `spawn_blocking`。
> 请求体上限：导入路由 10MB，其他接口默认 2MB（`DefaultBodyLimit`）。

基础用户导入每行使用同一事务中的 SAVEPOINT：数据库约束异常只回滚该行，
后续有效行继续写入，最终成功行统一提交；预校验不新增用户。
模板和错误报告生成通过 `kernel::xlsx::run` 调度，错误报告最多 500 行且不包含初始密码。

本地文件删除先提交元数据软删，再删除物理内容。提交失败必须保留原文件；物理删除失败
仅记录日志并保留软删记录及 storage_key，需运维重试清理。下载在权限和元数据读取完成后
释放只读事务，再读取磁盘；当前仍全量读入内存，尚未实现流式大文件下载。

### 15.4 导出

- 同步上限 5000 行（流式 `StreamBody`）。
- 超过走异步任务：游标分批读 → `rust_xlsxwriter` 边写边传对象存储 → 生成下载链接 → 站内信通知。
- 导出必须带**数据权限**过滤，并记审计（防批量拖库）。

> **现状**：已实现异步导出任务（`sys_export_task` + 后台 `run_export`），
> 单次最多 20000 行，不做流式（文件先在内存生成再落盘）。
> **基础层现状**：内核用户/审计导出通过 `xlsx::run_anyhow` 生成；
> 用户导入模板/错误报告及租户账单通过 `xlsx::run` 生成，均复用受控阻塞池。
> 外层 `tokio::spawn` 只负责调度；具体插件导出实现本轮不审改。
> 下载接口用 `state.storage.load` 一次性读入内存，不适合超大文件。

## 16. 插件运行时（后端视角）

> 契约细节见 `04-插件体系.md`，此处只讲运行时行为。

### 16.1 启动序列

```
1. 加载配置 → 初始化日志/追踪/指标
2. 连接 PG → 校验 schema 版本 → 获取迁移锁（advisory lock）
3. 收集 inventory 注册的插件 → 拓扑排序（depends_on）
4. 逐个插件：
   a. 校验 kernel_min 版本
   b. 建 schema（若不存在）
   c. 执行迁移（SET search_path）
   d. upsert 权限点/菜单/字典/任务定义
5. 调用各插件 on_start（并发，单个超时 10s，失败则整体启动失败）
6. 启动 outbox 派发器、任务调度器
7. 开始接收流量（readiness = true）
```

### 16.2 失败策略

| 场景 | 策略 |
|---|---|
| 插件迁移失败 | **整体启动失败**（不允许半迁移状态） |
| `on_start` 失败 | 默认失败即退出；可配置 `optional = true` 降级（插件路由返回 503） |
| 插件 panic | `CatchPanic` 捕获 → 该请求 500，进程存活（见 ADR-0004）；**连续 panic 熔断未实现** |
| 请求超时 | `TimeoutLayer` 返回 408 `problem+json`；只约束 handler，不含响应体传输 |
| 并发打满 | `ConcurrencyLimit + LoadShed` 立即 503 + `Retry-After`，不排队 |
| 阻塞池排队超时 | 503 + `Retry-After`（Argon2 / xlsx 场景，见 ADR-0005） |
| 数据库不可用 | 请求返回 500；`/readyz` 返回 503 并摘流 |

### 16.3 隔离边界（进程内）

进程内插件**没有内存隔离**，靠规范约束：

- 插件不得 `std::process::exit`、不得 `unsafe`（`#![forbid(unsafe_code)]`）。
- 插件不得 spawn 无限后台任务（必须用 kernel 提供的 `JobRunner`）。
- 插件不得直接读其他插件的表（DB role 只授本 schema）。
- 单个插件路由前缀固定 `/api/{id}`，禁止注册根路径。

## 17. 可观测埋点（后端侧）

| 类型 | 内容 |
|---|---|
| Trace | `http.request` → `service.{name}` → `db.query`（含 SQL 摘要，不含参数值） |
| Log | JSON 结构化：`ts, level, trace_id, tenant_id, user_id, plugin, route, status, latency_ms, err_code` |
| Metric | `http_requests_total{route,status}`、`http_request_duration_seconds`、`db_pool_connections`、`db_pool_idle`、`db_pool_saturated`、`session_cache_hits_total` / `misses_total` / `invalidations_total` |
| Audit | 独立的 `sys_audit_log`，与业务日志分离，防篡改（只追加） |

**指标基数**：`path` 使用 axum 的路由模板（`/api/system/users/{id}`），不是真实 URL；
未匹配的路由统一记为 `unmatched`。新增带变量路径的接口时不要用真实 URL 当标签，
否则 UUID 会把标签基数打爆。

**当前未埋的点**：`outbox_pending`、`job_failed_total`（对应能力尚未实现）。

**采样**：`observability.sample_ratio`（默认 0.1 = 10%），可用 `OTEL_TRACES_SAMPLER_ARG` 覆盖。
不用 SDK 默认值：`opentelemetry_sdk` 默认是 `ParentBased(AlwaysOn)`，即 100% 采样，
1000 QPS 下 exporter 自己就会成为瓶颈。
「错误请求 / 慢请求 100% 采样」需要自定义 Sampler（当前未实现，见 Backlog）。

## 18. 性能与容量

### 18.1 连接池公式

```
pool_size = ceil(QPS_peak × avg_query_time_s × safety_factor)
          = ceil(1000 × 0.005 × 4) ≈ 20  → 取 40（含后台任务）
每实例 40，8 实例 = 320 连接 → 超过 PG 舒适区（~500）
⇒ 引入 PgBouncer（transaction 模式）：应用侧 320 → 后端 50
```

**PgBouncer 注意**：transaction 模式不支持 `PREPARE`、会话级 `SET`、`LISTEN`。sqlx 需：

```rust
PgConnectOptions::new()
    .statement_cache_capacity(0)      // 关闭语句缓存
    .options([("application_name", "admin-api")])
```

会话级功能（`SET LOCAL` 在事务内可用；`LISTEN/NOTIFY` 不可用 → 改用轮询）。

### 18.2 N+1 防护

| 场景 | 反例 | 正解 |
|---|---|---|
| 列表带关联名称 | 循环查 `dept` | `JOIN` 或 `WHERE id = ANY($1)` 批量查后内存组装 |
| 详情多表 | 串行 5 次查询 | 单次多结果集 / `jsonb_agg` 聚合 |
| 权限校验 | 每请求查角色 | 登录时算好位图，缓存 |

CI 可选门禁：`sqlx` 查询计数断言（测试中 `SELECT` 次数 > 阈值即失败）。

### 18.3 压测目标

| 场景 | 并发 | P95 | 错误率 |
|---|---|---|---|
| 登录 | 100 | < 300ms | 0 |
| 列表（20 条，3 表 JOIN） | 500 | < 200ms | 0 |
| 详情 | 500 | < 100ms | 0 |
| 写操作（含 outbox） | 200 | < 250ms | 0 |
| 导出 5 万行 | 10 | < 60s（异步） | 0 |

**现有基线不能证明上表**：`apps/server/tests/bench.rs` 是 25 并发、走 `Router::oneshot`（不经过 TCP 与中间件的一部分），
只能作为回归对比，不能替代 k6 + 真实网关的压测。
过载场景（连接池打满 / 阻塞池排队）必须专门验证：期望结果是 **503 + `Retry-After`**，
而不是请求超时或进程 OOM。

## 19. 测试策略

| 层 | 工具 | 覆盖 | 要求 |
|---|---|---|---|
| 单元 | `#[test]` | 领域规则、状态机、校验 | 核心域 ≥ 80% |
| 集成 | `sqlx::test` | repo + service（真库、事务回滚） | 每插件必备 |
| 接口 | `axum::Router` + `oneshot` | 鉴权、错误码、分页 | 关键路径全覆盖 |
| 契约 | `insta` | openapi.json 快照 | 破坏性变更必红 |
| E2E | Playwright | 登录→CRUD→导出 | 冒烟 20 条 |
| 压测 | k6 | 见 18.3 | 每次大版本 |

```rust
#[sqlx::test(migrations = "./migrations")]
async fn create_customer_should_reject_duplicate(pool: PgPool) {

    assert_eq!(err.code(), "crm.customer.duplicated");
}
```

**测试数据**：每插件自带 `fixtures/`，禁止测试之间共享可变状态，禁止依赖执行顺序。

## 20. 后端反模式清单

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| handler 里开事务写多表 | 事务边界散落，无法复用 | service 层统一事务 |
| `anyhow!` 直接返回 | 错误码失控 | thiserror + AppError |
| `SELECT *` | 加列即破坏契约、浪费 IO | 显式列 |
| 用 `OFFSET` 翻深页 | 深分页 O(n) | 游标分页 |
| 缓存双写 | 数据不一致 | 更新 DB + 删缓存 |
| 在循环里 `await` 单条 SQL | N+1，接口 2s | 批量查询 |
| 用字符串拼 `ORDER BY` | 注入 | 白名单枚举 |
| 长事务包裹外部调用 | 连接被占满、锁等待 | 外部调用移出事务 |
| 同步导出大文件 | 内存爆、超时 | 异步任务 + 对象存储 |
| 日志打印请求体 | 泄漏密码/身份证 | 脱敏 + 白名单字段 |

## 接口文档（/docs）

- `GET /api/openapi.json`：运行时契约，包含内核 + 所有已注册插件；
- `GET /docs`：服务端渲染的只读 HTML 表格（方法/路径/说明/分组）。

不用 Swagger UI 的原因：`utoipa-swagger-ui` 构建期需要联网下载前端资源，
私有化/离线环境会直接编译失败；自渲染方案零 JS、零外部依赖。

## 异步导出（M4）

| 端点 | 作用 |
|---|---|
| `POST /api/system/export-tasks` | 创建任务，立即返回 id |
| `GET /api/system/export-tasks` | 轮询任务状态（只看自己的） |
| `GET /api/system/export-tasks/{id}/download` | 下载生成好的 xlsx |

- 后台用 `tokio::spawn` 执行，生成后写入对象存储（`{tenant}/exports/{task}.xlsx`）；
- 启动时 `recover_stale` 只回收「超过 15 分钟仍未完成」的 pending/running（滚动发布时避免误杀其他实例的任务），并删除 30 天前的成功/失败记录；
- 当前支持 `system.audit` 与 `system.users`，单文件上限 20000 行；
- 任务表已 **FORCE RLS**：启动恢复按租户循环设置 `app.tenant_id`，不跨租户裸更新。

> 插件要接入时，在 `run_export` 增加分支；如果类型继续增多，再抽成注册表。

# 06 · 平台化演进：从「管理后台」到「企业中台 + 多产品」

> 现状：一套管理后台（技术中台的控制面 + 一个参考应用）
> 目标：一个中台内核，承载 **CRM / IM / AI / IoT** 四条产品线
> 一句话：**中台提供"能力"，产品提供"场景"；中台不做业务，产品不重复造轮子**

---

## 0. 先说两句逆耳的

### 0.1 中台是"抽"出来的，不是"设计"出来的

行业里失败的中台有同一个死法：**先画一张大图，把所有能力都塞进中台，然后没有产品愿意用**。

正确顺序是：

```
先有 1~2 个产品跑通
  → 把重复出现的 3~5 个能力抽到中台（身份、权限、文件、消息、审计）
  → 中台只保留"被 ≥ 2 个产品验证过"的能力
  → 新产品接入时，中台能力不够就补，够就别动
```

**所以本文档的正确用法**：不是"照着一次建完"，而是"知道边界在哪，每上一个产品只补该补的那块"。

### 0.2 四条产品线的复杂度差 10 倍

| 产品 | 本质 | 相对现有架构的冲击 |
|---|---|---|
| CRM | 业务 CRUD + 流程 | **几乎为零**，就是插件 |
| IoT | 海量设备写入 + 时序 | 中（新增接入层与时序库） |
| IM | 长连接 + 消息一致性 | **大**（连接网关、消息存储、投递语义） |
| AI | 异构算力 + 流式 + 计量 | **大**（GPU 服务、Python 生态、成本控制） |

结论：**中台内核不动，动的是"接入层 + 异步骨干 + 数据分层"**。这三块现在缺，必须先补，否则后面每个产品都要重复造一遍。

## 1. 现有设计哪些撑得住、哪些撑不住

| 现有决策 | CRM | IM | AI | IoT | 判断 |
|---|---|---|---|---|---|
| 单二进制 + 插件 | ✅ 完美 | ❌ 连接层需独立扩缩容 | ❌ GPU 服务必须独立 | ❌ 接入层需独立集群 | **保留内核，服务可拆** |
| 仅 PG | ✅ | ❌ 消息量 10¹⁰ 级 | ⚠️ pgvector 起步够用 | ❌ 时序写入扛不住 | **PG 为主，按需分层** |
| Cookie 会话 | ✅ | ❌ 需 Token/长连接鉴权 | ⚠️ | ❌ 设备需证书 | **补 OAuth2/OIDC + 设备身份** |
| 同步请求 | ✅ | ❌ 消息推送是异步 | ❌ 推理要流式/异步 | ❌ MQTT 天然异步 | **补事件总线 + SSE/WS** |
| 进程内 outbox | ✅ | ❌ 跨服务 | ❌ | ❌ | **升级为平台级事件总线** |
| 编译期插件 | ✅ | ⚠️ 独立发布更合适 | ✅ | ✅ | **扩展为三级扩展模型** |
| 行级多租户 | ✅ | ✅ | ✅（按 token 计量） | ⚠️ 设备量巨大需独立分区 | **保留，扩展配额维度** |

**一句话**：内核（身份/租户/权限/审计/文件/配置/事件契约）**完全复用**；新增的是"接入层、异步骨干、数据分层"三件基础设施。

## 2. 目标分层架构

```
┌──────────────────────────────────────────────────────────────────┐
│ L3 产品与门户                                                      │
│  统一工作台 │ CRM 前端 │ IM 客户端(Web/桌面/移动) │ AI 应用 │ IoT 大屏 │
└───────────────────────────┬──────────────────────────────────────┘
┌───────────────────────────▼──────────────────────────────────────┐
│ 接入层                                                            │
│  API 网关(APISIX) │ BFF │ WS 网关 │ MQTT 接入 │ 开放平台(AppKey)   │
└───────────────────────────┬──────────────────────────────────────┘
┌───────────────────────────▼──────────────────────────────────────┐
│ L2 领域平台（各自独立部署，可独立扩缩容）                            │
│  CRM 服务 │ IM 服务(连接/消息/推送) │ AI 服务(网关/RAG/Agent)        │
│           │                          │ IoT 服务(设备/规则/OTA)      │
└───────────────────────────┬──────────────────────────────────────┘
┌───────────────────────────▼──────────────────────────────────────┐
│ L1 技术中台（共享内核，稳定优先）                                   │
│  IAM 统一身份 │ 租户组织 │ 权限( RBAC/ABAC/数据权限 ) │ 审计        │
│  消息中心 │ 文件媒体 │ 配置字典 │ 任务调度 │ 事件总线 │ 计量计费     │
│  工作流(轻量) │ 搜索 │ 通知(邮件/短信/推送) │ 开放平台               │
└───────────────────────────┬──────────────────────────────────────┘
┌───────────────────────────▼──────────────────────────────────────┐
│ L0 数据与基础设施                                                   │
│  PG(事务) │ Redis │ 时序库 │ 向量库 │ 消息存储 │ 对象存储 │ OLAP     │
│  K8s │ 可观测(OTel/Prom/Loki) │ CI/CD │ 密钥管理                     │
└──────────────────────────────────────────────────────────────────┘
```

**分层纪律**：
- L1 不得依赖 L2（中台不知道 CRM 的存在）
- L2 之间不得直接调用，只能走事件或 L1 能力
- L3 只能调 L1/L2 的公开 API，不得直连数据库

## 3. 中台能力地图（含准入标准）

### 3.1 能力清单

| 能力 | 提供的接口 | 被谁复用 | 优先级 |
|---|---|---|---|
| **IAM 统一身份** | OIDC/OAuth2、SSO、SCIM、MFA、设备身份 | 全部 | P0 |
| 租户与组织 | 租户生命周期、部门/岗位/人员 | 全部 | P0 |
| 权限中心 | RBAC + 数据权限 + 字段权限 + 策略引擎(ABAC) | 全部 | P0 |
| 审计中心 | 操作/登录/数据变更审计、留存、检索 | 全部 | P0 |
| 文件与媒体 | 预签名上传、图片处理、病毒扫描、水印 | CRM/IM/AI/IoT | P0 |
| 消息中心 | 站内信、邮件、短信、App 推送、模板 | 全部 | P0 |
| 配置中心 | 参数、字典、开关、灰度规则 | 全部 | P0 |
| 任务调度 | cron、延迟任务、分布式执行 | 全部 | P0 |
| **事件总线** | 发布/订阅、CloudEvents、重放 | 全部 | P0 |
| 计量计费 | 用量采集（API 调用/Token/设备数/存储） | SaaS | P1 |
| 搜索 | 全文检索、联想 | CRM/IM/AI | P1 |
| 工作流 | 轻量审批（状态机） | CRM/全部 | P1 |
| 开放平台 | AppKey/Secret、签名、限流、开发者门户 | 对外 | P2 |
| 低代码 | 表单/列表配置化 | 内部工具 | P3（谨慎） |

### 3.2 中台准入三原则（防止大泥球）

一条能力要进中台，必须**同时**满足：

1. **被 ≥ 2 个产品复用**（只有一个产品用 → 放产品里）
2. **不含业务语义**（"客户"是 CRM 的，"用户"是中台的）
3. **有明确 owner 与 SLA**（没人负责的能力不许进）

> 反例：「客户标签体系」看着通用，但它只服务 CRM → 放 CRM。等 IM 也要用时再抽。

### 3.3 中台退出机制

能力连续 2 个季度复用度 < 2 个产品 → 降级为产品内模块，从中台移出。**中台必须能瘦身，否则一定膨胀。**

## 4. 接入层重构

| 组件 | 选型 | 职责 |
|---|---|---|
| API 网关 | **APISIX**（或 Kong） | 路由、JWT 校验、限流、灰度、WAF、访问日志 |
| BFF | axum（可选，按产品） | 聚合裁剪、SSR、按端定制 |
| WS 网关 | axum + tokio（自研） | IM/通知长连接，独立扩缩容 |
| MQTT 接入 | **EMQX 集群**（不自研） | IoT 设备连接、认证、规则转发 |
| 开放平台网关 | APISIX 插件 + 签名校验 | 第三方 AppKey、配额、计费 |
| 服务间通信 | gRPC + mTLS | 内部调用，Protobuf 契约 |

**网关必须做的事**（应用层不再重复）：

```
TLS 终止 → JWT 验签（公钥缓存）→ 租户识别 → 限流（租户/用户/IP/路由）
→ 灰度路由（按 header/租户/比例）→ 上游负载均衡 → 超时/重试 → 访问日志
```

**关键**：JWT 验签放网关，应用只信任网关注入的 `X-User-Id / X-Tenant-Id` 头（并校验来源 IP/双向 TLS），避免每个服务重复实现。

## 5. 异步骨干

### 5.1 选型

| 方案 | 吞吐 | 运维 | 适用 |
|---|---|---|---|
| **NATS JetStream** | 高 | 低（单二进制） | 起步首选，事件总线 |
| Kafka | 极高 | 高（ZK/KRaft 集群） | IoT 海量数据管道、日志 |
| Redis Streams | 中 | 极低 | 轻量任务、已有 Redis |
| RabbitMQ | 中 | 中 | 复杂路由（不推荐新增） |

**建议**：中台事件总线用 **NATS JetStream**；IoT 数据管道单独用 Kafka（或直接 MQTT→TimescaleDB）；不引入两套以上。

### 5.2 事件契约

```json
{
  "specversion": "1.0",
  "id": "0192f3a1-...",
  "source": "crm",
  "type": "crm.customer.created",
  "subject": "customer/0192...",
  "time": "2026-10-28T08:00:00Z",
  "tenantid": "0192...",
  "datacontenttype": "application/json",
  "data": { "id": "...", "name": "..." }
}
```

| 规则 | 说明 |
|---|---|
| 标准 | CloudEvents 1.0（跨语言、跨产品统一） |
| 命名 | `{product}.{aggregate}.{action}`，过去式 |
| Schema | Protobuf/Avro + Schema Registry，**事件 schema 只增不改** |
| 语义 | 至少一次 + 消费端幂等（`event_id` 去重表） |
| 顺序 | 同 `subject` 保序（分区键 = subject） |
| 死信 | 重试 10 次进 DLQ，人工介入 |
| 重放 | 支持按时间/偏移重放（新消费者初始化） |

### 5.3 事件分类

| 类型 | 例 | 消费者 |
|---|---|---|
| 域事件 | `crm.customer.created` | 同产品内部 |
| 集成事件 | `iam.user.disabled` | 跨产品（IM 要踢人、AI 要停配额） |
| 系统事件 | `sys.job.failed` | 运维告警 |

**outbox 升级**：插件内 outbox 保留（保证本地事务原子），派发器改为投递到 NATS，跨产品由总线负责。**不引入分布式事务**，最终一致 + 对账任务。

## 6. 数据分层

| 数据类型 | 起步 | 规模化 | 触发切换的条件 |
|---|---|---|---|
| 事务（租户/权限/CRM） | **PG** | PG 主从 + 分区 | 单表 > 1 亿 |
| 消息（IM） | PG 分区（按月） | **ScyllaDB / TiDB** | 消息 > 5 亿条或写入 > 5000 TPS |
| 时序（IoT） | **TimescaleDB**（PG 扩展） | TDengine / InfluxDB | 设备 > 5 万或写入 > 10 万点/秒 |
| 向量（AI） | **pgvector** | Milvus / Qdrant | 向量 > 1000 万或 QPS > 200 |
| 对象（文件/固件/模型） | MinIO | S3 / OSS | 容量 > 10TB |
| OLAP（报表/行为） | PG 只读副本 + 物化视图 | ClickHouse / Doris | 报表查询 > 5s |
| 搜索 | PG FTS / pg_trgm | OpenSearch / Meilisearch | 需要分词/高亮/联想 |
| 缓存 | Redis | Redis Cluster | 单实例内存 > 32GB |

### 铁律

> **能放 PG 就放 PG。每引入一个新存储 = +1 套备份、+1 套监控、+1 个故障域、+1 种技能要求。**
> 上表"起步"列足以支撑前 2–3 年，**不要提前上 ScyllaDB/ClickHouse**。

## 7. 扩展模型升级：三级

| 级别 | 形态 | 适用 | 发布 |
|---|---|---|---|
| **L1 Kernel Extension** | crate（编译期） | 系统管理类、强一致小功能 | 跟内核发版 |
| **L2 Service Plugin** | 独立服务 + 能力清单 | IM / AI / IoT / 大业务域 | 独立发版 |
| **L3 UI Plugin** | 前端包（构建期或 MF） | 所有产品的页面 | 独立发版 |

### 7.1 服务插件清单（`plugin.yaml`）

```yaml
id: im
name: 即时通讯
version: 1.4.0
kind: service            # kernel | service
kernelRange: ">=1.2.0 <2.0.0"
basePath: /api/im
upstream: http://im-gateway:8080
health: /healthz

permissions:
  - im:conversation:list
  - im:message:send
menus:
  - { title: 消息中心, path: /im, icon: message }

events:
  publishes: [im.message.sent, im.group.created]
  consumes: [iam.user.disabled, iam.user.deleted]

resources:               # 声明占用的基础设施，便于容量规划
  - { kind: pgsql, schema: plg_im }
  - { kind: redis, db: 3 }
  - { kind: objectstore, bucket: im-media }
```

**能力注册中心**（中台内置）：

```sql
CREATE TABLE sys.service (
  id text PRIMARY KEY, name text NOT NULL, version text NOT NULL,
  kind text NOT NULL, base_path text NOT NULL, upstream text,
  plugin_yaml jsonb NOT NULL, health_url text,
  status text NOT NULL DEFAULT 'unknown',      -- healthy|degraded|down
  last_heartbeat timestamptz, owner text NOT NULL
);
```

- 服务启动时注册 + 每 15s 心跳
- 网关从注册中心拉路由（或服务发现）
- 控制台展示"服务拓扑 + 健康 + 版本矩阵"

### 7.2 内核与服务的边界

| 判断 | 内嵌（L1） | 独立（L2） |
|---|---|---|
| 调用频率 | 极高频、需事务 | 中低频 |
| 数据一致性 | 与内核同库强一致 | 最终一致可接受 |
| 资源画像 | 与主应用相近 | 差异大（GPU/长连接/IO 密集） |
| 发布节奏 | 跟内核 | 独立 |
| 团队 | 平台组 | 产品组 |

## 8. 各产品线架构要点

### 8.1 CRM（业务型 —— 中台的"样板间"）

| 项 | 设计 |
|---|---|
| 形态 | L1 编译期插件（小客户）或 L2 服务（大客户） |
| 领域 | 客户/联系人/商机/合同/回款/跟进记录/公海池 |
| 复用中台 | IAM（用户组织）、权限（数据范围=本人/部门/团队）、文件（附件）、消息（提醒）、审计、工作流（合同审批） |
| 关键设计 | 数据权限是核心（销售只能看自己的客户）；公海池用"归属 + 回收规则"；跟进记录用时间线 |
| 价值 | **验证中台复用率**：CRM 若还要自己写登录/权限/文件，说明中台不合格 |

### 8.2 IM（通信型 —— 最不像管理后台）

| 层 | 设计 |
|---|---|
| 连接层 | axum WebSocket，**独立网关**，无状态 + 一致性哈希路由；单机 5–10 万连接 |
| 协议 | JSON over WS（起步）/ Protobuf（优化）；心跳 30s；断线重连带 `last_seq` 补偿 |
| 会话 ID | 单聊 `hash(min(uid), max(uid))`；群聊 `group_id`；保证幂等 |
| 序列号 | 每会话单调递增 `seq`（Redis `INCR` 或 PG 序列），**消息顺序的唯一依据** |
| 投递 | 在线直推（路由表查连接）→ 离线存收件箱 → 上线拉取增量 |
| 多端同步 | 每用户"收件箱 + 已读位点"，按 `seq` 增量同步 |
| 扩散策略 | 小群（< 500）写扩散（每人一条收件箱）；大群读扩散（只存一份，读时拉） |
| 存储 | 热：Redis Stream（最近 7 天）；冷：PG 分区 → 规模化换 ScyllaDB |
| 推送 | APNs / FCM / 华为 / 小米 / OPPO / vivo 通道适配（中台消息中心统一封装） |
| 内容安全 | 敏感词（DFA）、图片审核、举报、撤回时限 |
| 复用中台 | IAM（用户/组织/在线状态来源）、文件（图片/语音）、审计、通知 |

> **Rust 在 IM 的高光点**：连接网关的内存占用与 GC 停顿。同等连接数，Rust 网关内存约为 Java 的 1/3–1/2，且无 GC 抖动。

**IM 三个必须提前定的语义**（后期改不动）：
1. 消息 ID 生成规则（ULID / Snowflake）与全局唯一性
2. 会话内 `seq` 的分配者（Redis vs DB）与故障时的连续性
3. 已读回执的粒度（会话级 / 消息级）

### 8.3 AI（智能型 —— 异构是常态）

| 层 | 设计 |
|---|---|
| 模型网关 | 统一 OpenAI 兼容协议；按租户/场景路由模型；配额、降级、重试 |
| 推理服务 | vLLM / TGI（GPU，Python），Rust 只做网关与编排 |
| RAG | 文档解析（Python）→ 分块 → embedding → pgvector → 检索 → rerank → 拼装 |
| Agent | 工具调用（MCP 协议）、多步编排、人工确认节点、超时与预算 |
| 流式 | SSE 透传 + 背压；首 token 延迟是核心指标 |
| Prompt 管理 | 版本化、灰度、A/B、评测集回归 |
| 成本 | token 计量、租户配额、语义缓存、小模型兜底 |
| 安全 | 输入输出审核、PII 脱敏、越狱检测、审计留痕 |
| 复用中台 | IAM、租户配额、文件（知识库）、审计、计量计费 |

**边界**：AI 的 Python 生态无法绕开，**不要用 Rust 重写推理**。Rust 负责"网关 + 编排 + 鉴权 + 计量"，Python 负责"模型 + 数据处理"。

### 8.4 IoT（设备型 —— 海量写入）

| 层 | 设计 |
|---|---|
| 接入 | **EMQX 集群**（不自研 MQTT Broker）+ 设备证书 mTLS + 一机一密 |
| 协议适配 | 边缘网关支持 Modbus / OPC-UA / BACnet / BLE，转 MQTT |
| 设备模型 | 产品（Product）→ 设备（Device）→ 物模型（属性/事件/服务） |
| 设备影子 | 期望状态 vs 上报状态，指令下发用影子对齐 |
| 时序 | TimescaleDB hypertable（按天分区 + 压缩） |
| 规则引擎 | 阈值/离线/连续 N 次触发；动作：告警、联动、Webhook |
| 告警 | 抖动抑制、静默期、升级策略、通知中台 |
| OTA | 分批次灰度、签名校验、断点续传、失败回滚 |
| 边缘 | **Rust 边缘网关**（交叉编译 ARM，单二进制，无运行时依赖）—— 这是 Rust 相对 Java 的绝对优势 |
| 复用中台 | 租户、权限、文件（固件包）、审计、计量（设备数） |

**IoT 与多租户的冲突**：设备量可能百万级，行级 RLS 会成为瓶颈 → 设备表按 `tenant_id` 哈希分区或独立库，**不要和大客户共用一个行级策略**。

## 9. 多语言策略

| 语言 | 职责 | 理由 |
|---|---|---|
| **Rust** | 中台核心、API/WS 网关、IM 连接层、IoT 边缘、高性能服务 | 内存安全、无 GC、单二进制、边缘友好 |
| **Python** | AI 推理、RAG、数据处理、算法 | 生态无可替代 |
| **Go**（可选） | 运维工具、K8s Operator | 云原生生态 |
| **TypeScript** | 前端、BFF（可选） | — |

**解耦靠协议，不靠语言**：

```
内部同步调用：gRPC + Protobuf（强类型、跨语言、代码生成）
对外 API：OpenAPI 3.1（REST）
事件：CloudEvents + Protobuf/Avro
消息队列契约：AsyncAPI
可观测：OpenTelemetry（跨语言统一 trace）
```

**代价要认**：多语言 = 多套构建、多套依赖、多套调试。**每引入一种语言，必须有一个团队能长期维护它**。

## 10. 部署形态演进

| 形态 | 组成 | 适用 | 交付 |
|---|---|---|---|
| **S 单体** | 1 二进制（中台 + CRM） | 中小企业私有化 | tar + docker compose |
| **M 混合** | 中台单体 + 3~5 个服务 + 单 PG | 中型客户 | docker compose / 单 K8s 命名空间 |
| **L 平台** | K8s 多服务 + PG 集群 + 消息总线 + 独立存储 | 大型客户 / SaaS | Helm Chart |

**同一套代码三种形态**：靠 `plugin.yaml` 的 `upstream` 配置决定"内嵌 or 远程"。内嵌 = 空 upstream，远程 = 填地址。**代码零改动。**

## 11. 演进路线（按风险与价值排序）

| 阶段 | 内容 | 为什么在这个位置 |
|---|---|---|
| **P0** | 中台内核（本文档 01–05） | 一切的地基 |
| **P1** | **CRM** | 最接近现有形态，用来验证"中台能力是否真的可复用"。**CRM 写不出来的能力，就是中台缺的能力** |
| **P2** | **IoT** | 引入时序库与 MQTT 接入，验证"高写入 + 边缘 Rust"；对现有架构冲击中等 |
| **P3** | **IM** | 长连接网关 + 消息存储 + 投递语义，冲击最大，必须等中台身份/审计稳定 |
| **P4** | **AI** | GPU 与 Python 异构，运维复杂度最高；但业务价值可能最高，可按商业节奏提前 |

> 若 AI 是商业优先（大概率），可把 P4 提前到 P2，但**必须先把"计量计费 + 配额 + 审计"做完**，否则 AI 的成本会失控。

## 12. 中台治理（决定能活多久）

| 机制 | 内容 |
|---|---|
| 能力准入 | 三原则（复用 ≥ 2、无业务语义、有 owner） |
| 能力退出 | 连续 2 季度复用 < 2 → 降级出中台 |
| 版本兼容 | N-1 版本兼容 ≥ 6 个月；破坏性变更需公告 + 迁移工具 |
| 服务目录 | 每个服务有 owner、SLA、依赖图、Runbook |
| 复用度度量 | 每季度统计"能力 × 产品"调用矩阵，作为中台 KPI |
| 接口人 | 每个产品团队指定 1 名中台接口人，双周对齐 |
| 变更评审 | 中台核心接口变更需架构委员会（3 人）通过 |
| 账单 | 中台资源按产品分摊（云成本 / 人力），避免"公共地悲剧" |

**中台团队规模参考**：4 条产品线时，中台 8–12 人（后端 6、前端 2、SRE 2），产品团队各自 5–10 人。中台人太少会成为瓶颈，太多会自我膨胀。

## 13. 风险清单

| 风险 | 表现 | 对策 |
|---|---|---|
| **过早平台化** | 4 条产品线同时开工，每条都半成品 | 单产品先跑通，能力按需抽取 |
| 中台变瓶颈 | 所有需求排队等中台排期 | 中台只做"能力"，业务逻辑还给产品；提供扩展点 |
| 存储碎片化 | 5 种数据库，运维崩溃 | 能放 PG 就放 PG，切换有条件 |
| 多语言失控 | Python 服务无人维护 | 每种语言必须有 owner 团队 |
| 事件契约腐化 | 事件字段随意改，消费方崩 | Schema Registry + 只增不改 |
| 多租户不一致 | 四个产品四种隔离方式 | 中台统一租户模型，产品不得自定义 |
| 长连接成本 | IM 网关机器费用高 | 连接数分级定价；心跳与压缩优化 |
| AI 成本失控 | 单租户跑满 GPU | 配额 + 计量 + 降级到小模型 |
| 设备安全 | 固件被刷、设备被仿冒 | 一机一密 + 证书轮换 + 固件签名 |

---

## 14. 一句话总结

> **中台是"被复用出来的"，不是"设计出来的"。**
> 先做 CRM 验证内核，再按"写入型（IoT）→ 连接型（IM）→ 智能型（AI）"逐步加，每加一条产品线只补它真正需要的那块基础设施；内核（身份/租户/权限/审计/文件/事件）始终只有一份。

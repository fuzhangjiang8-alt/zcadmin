# 07 · AI 原生开发与持续迭代

> 前提：**全部代码由 AI 生成，人只做规格、评审与架构决策**
> 结论：架构的目标不是"让 AI 更聪明"，而是**让 AI 的错误在 10 秒内暴露**

---

## 0. AI 写代码的三种失败模式

| 失败模式 | 表现 | 根因 |
|---|---|---|
| **幻觉** | 编造不存在的 API、crate、字段、配置项 | 上下文不足 + 无编译期校验 |
| **局部正确、整体破坏** | 改 A 功能，B 功能悄悄挂了 | 改动半径大 + 缺回归测试 |
| **风格漂移** | 同一个功能三种写法，越改越乱 | 无黄金样例 + 无强制格式化 |

架构能做的三件事：**给确定模板、压缩改动半径、建立秒级反馈**。

---

## 1. 核心原则

> **把 AI 当成"高速但不确定"的工程师：给它护栏、给它样例、给它验收标准，而不是给它自由。**

五条推论：

1. **能生成的绝不手写**（schema → 代码）
2. **能编译期发现的绝不留到运行期**（类型、契约、快照）
3. **一个功能只落在 5–8 个文件里**（垂直切片）
4. **每条规则都有机器可执行的检查**（CI 门禁）
5. **每个目录都有给 AI 看的说明书**（CONTEXT.md）

## 2. 支柱一：Schema 驱动（最大杠杆）

### 2.1 唯一真相源

```
schema/{plugin}/{entity}.toml   ← 人写（或 AI 根据需求写，人审）
        │
        ├─▶ migrations/*.sql            （DDL）
        ├─▶ src/domain/{entity}.rs      （实体 + 校验）
        ├─▶ src/repo/{entity}.rs        （CRUD + 分页 + 数据权限）
        ├─▶ src/service/{entity}.rs     （骨架，业务规则留空 TODO）
        ├─▶ src/api/{entity}.rs         （handler + utoipa 注解）
        ├─▶ permissions / menus / dicts （种子数据）
        ├─▶ openapi.json                （契约）
        ├─▶ packages/types/api.d.ts     （前端类型）
        ├─▶ plugins-web/{id}/views/{entity}/List.vue / Form.vue
        └─▶ tests/{entity}_test.rs      （集成测试骨架）
```

**AI 的工作从"写 1000 行代码"变成"在 3 个 TODO 处填业务规则"** —— 这是提效与稳定的关键。

### 2.2 Schema DSL 示例

```toml
# schema/crm/customer.toml
[table]
name    = "customer"
schema  = "plg_crm"
comment = "客户"

[[field]]
name     = "code"
type     = "varchar(32)"
required = true
unique   = true
label    = "客户编码"
list     = true
search   = "eq"          # eq|ct|in|between

[[field]]
name     = "name"
type     = "varchar(64)"
required = true
label    = "客户名称"
list     = true
search   = "ct"

[[field]]
name    = "level"
type    = "dict:customer_level"
label   = "客户等级"
list    = true

[[field]]
name    = "credit_limit"
type    = "numeric(20,4)"
label   = "信用额度"
perm    = "crm:customer:view_amount"   # 字段级权限

[permissions]
prefix  = "crm:customer"               # 自动展开 list/get/add/edit/delete/export

[menu]
parent  = "/crm"
title   = "客户管理"
icon    = "team"

[data_scope]
enabled = true                          # 生成数据权限注入代码
owner_field = "owner_id"
dept_field  = "dept_id"
```

### 2.3 生成命令

```bash
cargo xtask gen schema/crm/customer.toml
# → 生成 14 个文件，其中 3 处标 // TODO(ai): 业务规则
# → 自动注册权限点、菜单、OpenAPI、前端路由
# → 生成物头部带 // @generated，禁止手改
```

**校验**：CI 比对"schema 重新生成后的 diff"，不为空即失败 —— 防止有人（或 AI）绕过生成器手改生成物。

### 2.4 生成物与手写物的边界

| 类型 | 谁写 | 规则 |
|---|---|---|
| 迁移 / 实体 / repo / DTO / handler / 前端页面骨架 | 生成器 | 头部 `@generated`，禁止手改 |
| service 业务规则 / 状态机 / 校验 | AI + 人审 | 手写区，文件内用 `// ---- 手写区 ----` 标记 |
| 复杂查询 / 报表 SQL | AI + 人审 | 手写，必须有 EXPLAIN 记录 |
| 架构 / 契约 / ADR | 人 | AI 不参与决策 |

## 3. 支柱二：契约先行 + 快照锁

| 契约 | 生成方式 | 锁定方式 |
|---|---|---|
| HTTP API | utoipa 注解 → `openapi.json` | `insta` 快照 + 破坏性变更检测 |
| 前端类型 | `openapi-typescript` | 生成物入库，CI diff |
| 事件 | CloudEvents schema（Protobuf/JSON Schema） | Schema Registry + 只增不改检查 |
| 数据库 | 迁移文件 | 已发布迁移 hash 校验（改动即失败） |
| 权限点 | `permissions()` 声明 | 前后端一致性校验 `xtask check-perms` |

**效果**：AI 想"顺手重构"一个字段名，五道门禁会拦住它 —— 这是好事。

## 4. 支柱三：秒级反馈回路

### 4.1 时间预算（架构级约束）

| 操作 | 预算 | 超标后果 |
|---|---|---|
| `cargo check -p plugin-x` | **< 3s**（增量） | AI 迭代变慢，开始"猜"而不"验" |
| `cargo clippy -p plugin-x` | < 10s | 同上 |
| `cargo nextest -p plugin-x` | < 30s | 测试被跳过 |
| `cargo xtask verify`（全量） | < 3min | 提交前不愿跑 |
| `vue-tsc --noEmit` | < 20s | 类型错误漏检 |
| `vitest run`（单包） | < 30s | — |
| Vite HMR | < 1s | — |

### 4.2 保证手段

| 手段 | 说明 |
|---|---|
| workspace 拆分 | 每个插件独立 crate，改一个不重编全部 |
| 避免巨型泛型 | 泛型嵌套是编译时间杀手，超过 3 层就重构 |
| `lld` / `mold` 链接器 | 链接时间降 50%+ |
| `sccache` | CI 与本地共享缓存 |
| dev profile 优化 | `debug = 1`（不是 2）、`incremental = true` |
| 依赖瘦身 | `cargo machete` 清理未用依赖；feature 门控 |
| 前端按包构建 | `pnpm --filter` 只构建改动的包 |

> **反面案例**：单 crate 20 万行、`cargo check` 90 秒 → AI 一轮改动要等 3 分钟 → 它会开始一次改 20 个文件"赌一把" → 正确率暴跌。**编译速度就是 AI 的生产力。**

### 4.3 一键验收

```bash
cargo xtask verify
# 依次执行：
# 1. cargo fmt --check
# 2. cargo clippy --all-targets -- -D warnings
# 3. cargo nextest run
# 4. cargo xtask arch-check      （依赖方向/文件行数/unsafe/生成物未被手改）
# 5. cargo xtask check-perms     （前后端权限点一致）
# 6. cargo xtask openapi --check （契约快照）
# 7. pnpm typecheck && pnpm lint && pnpm test
```

**完成定义（DoD）**：`xtask verify` 全绿 + PR 描述含 Spec 链接 + 影响面说明。AI 不允许以"应该没问题"结案。

## 5. 支柱四：压缩改动半径

| 约束 | 阈值 | 检查 |
|---|---|---|
| 单文件行数 | ≤ 300（生成物除外） | `arch-check` |
| 单函数行数 | ≤ 50 | clippy `too_many_lines` |
| 单 PR 改动 | ≤ 400 行 | CI 提示（超了要求拆分） |
| 插件间依赖 | 0（只能走事件） | `arch-check` |
| 循环依赖 | 0 | `cargo` 本身 + 架构检查 |

**为什么重要**：AI 的上下文窗口有限，文件越大它越容易"看到一半就改"。**300 行是一个经验阈值**：小于它，AI 能完整理解；大于它，漏改概率显著上升。

## 6. 支柱五：机器可读的上下文

### 6.1 仓库级 `AGENTS.md`（仓库根，所有 AI 工具都读）

```markdown
# AGENTS.md

## 开始任何任务前必读
- docs/企业级管理后台-架构设计.md（总览与 ADR）
- docs/01-后端架构.md 第 4 节（分层规范）
- 本插件目录下的 CONTEXT.md

## 铁律（违反即拒绝合并）
1. handler 不得写 SQL，repo 不得做业务判断
2. 不得手改 `@generated` 文件；改 schema 后重新生成
3. 不得修改已发布的迁移文件（只能新增）
4. 新增第三方依赖必须先在 docs/adr/ 提 ADR 并获批准
5. 不得使用 `unsafe`；不得 `unwrap()`（测试除外）
6. 不得跨插件 `use`；跨插件通信只能用事件
7. 每个写接口必须有权限点；每条查询必须带数据权限
8. 新增/修改代码后必须跑 `cargo xtask verify`

## 常用命令
- `cargo xtask doctor`            环境检查
- `cargo xtask gen <schema.toml>` 生成 CRUD
- `cargo xtask new-plugin <id>`   新建插件
- `cargo xtask verify`            全量验收
- `pnpm dev` / `pnpm gen:api`

## 完成定义（DoD）
- [ ] verify 全绿
- [ ] 新增/修改的权限点已声明并前后端一致
- [ ] 涉及表的改动有迁移 + 回滚说明
- [ ] PR 描述含：改了什么、为什么、影响面、如何验证
```

### 6.2 插件级 `CONTEXT.md`（领域知识，AI 的"业务内存"）

```markdown
# CRM 插件上下文

## 领域术语
- 客户（Customer）：签约主体，唯一标识为 code（租户内唯一）
- 公海（Pool）：无归属的客户池，销售可领取，30 天未跟进自动回收
- 商机（Opportunity）：客户下的销售机会，阶段推进不可逆

## 表
| 表 | 说明 | 关键约束 |
| customer | 客户主表 | (tenant_id, code) 唯一，软删 |
| contact  | 联系人 | 一个客户多个联系人，最多 1 个主联系人 |

## 权限点
crm:customer:{list,get,add,edit,delete,export}

## 事件
- 发布：crm.customer.created / crm.customer.transferred
- 订阅：iam.user.disabled（负责人离职 → 客户回公海）

## 状态机
potential → following → signed → lost（lost 可复活）

## 禁止事项

```

## 8. 支柱七：防幻觉的硬约束

| 风险 | 约束 |
|---|---|
| 编造 crate | `cargo deny` 白名单 + 新依赖需 ADR |
| 编造 API | 本地 `cargo doc --open` + `docs/api-index.md` 索引；禁止凭记忆写 |
| 编造配置项 | 配置用 `serde` 强类型 + `deny_unknown_fields`，写错启动即失败 |
| 编造字段 | sqlx 编译期校验（连真库或离线缓存） |
| 自由 HTTP 调用 | 统一 `HttpClient`，域名白名单，禁止裸 `reqwest` |
| 偷偷改契约 | OpenAPI 快照 + 迁移 hash |
| 大段复制粘贴 | 重复代码检测（`jscpd`）+ 抽象到 `shared` |
| 忽略错误处理 | clippy `unwrap_used` / `expect_used` 设为 deny |

## 9. AI 开发工作流：Spec → Plan → Code → Verify → Review

```
① Spec（人写，20 行以内）
   目标 / 验收标准 / 涉及表 / 权限点 / 边界条件 / 不做什么

② Plan（AI 产出，人审 2 分钟）
   要改哪些文件、新增哪些、风险点、需要确认的问题

③ Generate（AI 执行）
   xtask gen 出骨架 → 填 3 处 TODO → 生成前端页面 → 补测试

④ Verify（AI 自测）
   cargo xtask verify → 失败自己修，最多 3 轮，仍失败则上报

⑤ Review（人审 20%）
   只看五件事：领域规则对不对、事务边界、权限、SQL 性能、错误码
```

### 9.1 人机分工量化

| 工作类型 | AI 占比 | 人占比 | 说明 |
|---|---|---|---|
| CRUD / 表单 / 表格 | 95% | 5% | 生成器覆盖 |
| 测试用例 | 90% | 10% | 边界条件由人补 |
| 前端页面 | 90% | 10% | 组件库 + 模板 |
| 领域规则 | 40% | 60% | 业务语义 AI 猜不准 |
| 事务 / 并发 | 30% | 70% | 一旦错就是数据事故 |
| 安全 / 权限 | 20% | 80% | 越权是最高频漏洞 |
| 性能优化 | 30% | 70% | 需要真实数据 |
| 架构决策 | 0% | 100% | — |

### 9.2 Spec 模板

```markdown
# Spec: 客户批量导入

## 目标
支持 Excel 导入客户，单次 ≤ 5 万行，失败行可下载。

## 验收标准
- [ ] 模板下载可用
- [ ] 重复 code 跳过并计入"忽略数"
- [ ] 错误行返回行号 + 原因
- [ ] 导入完成发站内信
- [ ] 仅有 crm:customer:import 权限可调用

## 涉及
表：plg_crm.customer   权限：crm:customer:import   事件：crm.customer.imported

## 边界
- 文件 > 10MB 拒绝
- 全部失败则整体回滚
- 并发导入同一租户加锁

## 不做
- 不做增量更新（仅新增）
```

> **Spec 的质量决定 AI 产出的质量**。20 行 Spec 能省 2 小时返工。

## 10. 代码规范为 AI 优化

| 规则 | 原因 |
|---|---|
| 命名唯一：只用 `get/list/create/update/delete` | 避免 AI 在 fetch/query/load 之间随机选 |
| 显式优于隐式：不用宏生成业务逻辑 | 宏对 AI 不透明，改不动 |
| 一层抽象：不做 `Repository<T>` 泛型套娃 | 泛型对 AI 是黑箱 |
| 错误必须显式处理 | 禁止 `unwrap`，`?` + 统一 `AppError` |
| 注释写"为什么" | "是什么"由代码表达 |
| 单函数 ≤ 50 行 | 超过就是职责不清 |
| 不用 `unsafe` | 100% 禁止（`#![forbid(unsafe_code)]`） |
| 依赖注入用显式字段 | 不用 DI 容器/反射 |

> **注释规范单独成文**：见 `docs/09-注释与文档规范.md`。
> 核心要求：文件头写清职责与边界、公开项写清失败语义、注释只讲"为什么"、TODO 必须带负责人与替代方案。
> 编译器层面用 `#![deny(missing_docs)]` + `#![forbid(unsafe_code)]` 兜底，不靠自觉。

## 11. 生成器清单（`cargo xtask`）

| 命令 | 作用 | 频率 |
|---|---|---|
| `new-plugin <id>` | 插件骨架（后端 crate + 前端包 + 迁移 + 权限 + 测试 + CONTEXT.md） | 每新业务域 |
| `gen <schema.toml>` | schema → 迁移 SQL + Rust 模型/接口/router（前端页面手写或后续版本生成） | 每新表 |
| `openapi` | 导出 `contracts/openapi.json`，随后在 frontend 执行 `npm run gen:api` | 每次接口变更 |
| `arch-check` | 当前检查 kernel 不依赖插件、插件源码不直接互相引用 | 每次 CI |
| `check-perms` | 权限声明、前端按钮、权限常量与错误码契约一致性 | 每次 CI |
| `verify` | fmt → clippy → 普通测试 → 架构 → RLS 静态覆盖 → 权限/错误码契约，共六步 | 每次提交 |
| `doctor` | 工具链版本、配置文件与 DATABASE_URL 存在性；不探测数据库/端口 | 新人/AI 首次 |

本表以 `crates/xtask/src/main.rs` 当前分发为准。`gen-api`、`seed`、`explain-check` 不是已实现的 xtask 子命令；
文件行数/unsafe/生成物 hash 等完整架构门禁仍是目标，不应从 `arch-check` 通过推断已全部检查。

`verify` 默认不执行 `#[ignore]` 真库用例，也不构建前端或重新生成契约。基础功能提交应另外执行：

```bash
# DATABASE_URL 使用测试环境，sqlx::test 需要创建数据库权限
cargo test -p kernel --test session_atomicity --test file_atomicity --test user_import_atomicity -- --ignored --test-threads=1
cargo xtask openapi
cd frontend
npm run gen:api
npm test
npm run build
```

RLS owner/普通角色验证按 CI integration job 单独执行；基础真库测试不替代生产角色隔离与真实部署验证。

### 11.1 schema 示例

```toml

plugin = "crm"
table = "contact"
name = "联系人"
route = "/contacts"
owner_field = "owner_id"   # 数据权限：self 依据
dept_field = "dept_id"     # 数据权限：dept 依据

[[field]]

```

执行 `cargo xtask gen schema/crm/contact.toml` 生成后，按提示在插件里挂载两行即可。

### 11.2 生成物的契约

生成器会为 5 个 handler（list / detail / create / update / delete）生成 `#[utoipa::path(...)]`，路径统一为 `/api/{plugin}{route}`（如 `/api/crm/contacts`、`/api/crm/contacts/{id}`），配套的 VO / 请求结构体也已派生 `ToSchema`。

但注解只是声明，还要在插件的 `OpenApi` 实现里登记才会进契约——即生成文件头部第 3 步的提示：

```rust
#[derive(utoipa::OpenApi)]
#[openapi(
    paths(contact::list, contact::detail, contact::create, contact::update, contact::delete),
    components(schemas(
        contact::ContactVo,
        contact::CreateContactRequest,
        contact::UpdateContactRequest,
    )),
)]
pub struct CrmApi;
```

- `paths(...)` 决定契约里有没有这些接口，漏登记就查不到；
- `components(schemas(...))` 决定模型定义是否完整，漏登记则请求/响应 schema 缺失。

> 提示：生成物一旦手工改过（例如迁移到 `TenantTx`、补数据权限/审计），不要直接重跑 `cargo xtask gen`，否则模板会覆盖这些改造。请先备份并 diff，或把手工改动同步回模板后再生成。

## 12. 持续迭代机制

### 12.1 节奏

| 周期 | 内容 |
|---|---|
| 每日 | 主干合并（trunk-based），随时可发布 |
| 双周 | 产品迭代（业务功能） |
| 每月 | 平台版本（内核/组件库），统一升级依赖 |
| 每季度 | 架构回顾：ADR 复审、技术债清理、容量评估 |
| 每半年 | 大版本（可含破坏性变更 + 迁移工具） |

### 12.2 兼容策略

| 对象 | 兼容期 | 机制 |
|---|---|---|
| HTTP API | N-1，≥ 6 个月 | 版本前缀 + 弃用响应头 `Deprecation`/`Sunset` |
| 事件 Schema | 永久只增不改 | 新增字段可选；删除需升主版本 |
| 数据库 | Expand-Contract | 见 03 文档第 15 节 |
| 插件契约 | trait 变更需默认实现 | 否则视为内核 MAJOR |
| 前端组件 API | N-1 | 旧 props 保留 1 个版本并告警 |

### 12.3 技术债预算

- 每迭代 **20% 工时**用于还债（不是"有空再说"）。
- 债务登记 `docs/tech-debt.md`：ID / 描述 / 影响 / 修复成本 / 计划版本。
- **强制重构触发条件**（任一命中）：
  - 同一段逻辑复制 ≥ 3 处
  - 改一个需求要动 ≥ 5 个文件
  - 单文件 > 300 行
  - 测试覆盖 < 50% 的核心模块
  - 线上缺陷在同一模块重复出现 2 次

### 12.4 数据驱动的优化闭环

```
采集（OTel / 埋点 / 慢查询）
  → 每周看板复盘（P95、错误率、慢 SQL TOP10、包体积）
  → 选 1–2 个瓶颈
  → 优化（加索引 / 改 SQL / 加缓存 / 拆包）
  → 灰度验证（对比指标）
  → 固化（写进基线，CI 卡口）
```

**原则**：没有度量数据的"优化"一律不做（多数是拍脑袋）。

### 12.5 特性开关与灰度

| 规则 | 说明 |
|---|---|
| 默认关闭 | 新功能上线先关，按租户/用户/比例放量 |
| 命名 | `{product}.{feature}.v{n}` |
| 生命周期 | ≤ 3 个月，全量后必须删除（防开关堆积） |
| 登记 | `sys_feature` 表 + 控制台可视 |
| 回滚 | 关开关即回滚，不需发版 |

### 12.6 DORA 四指标（团队效能）

| 指标 | 目标 |
|---|---|
| 部署频率 | 每日 ≥ 1 次 |
| 变更前置时间 | < 1 天 |
| 变更失败率 | < 5% |
| 故障恢复时间 | < 1 小时 |

## 13. 质量度量（AI 是否真的提效）

| 指标 | 目标 | 采集方式 |
|---|---|---|
| 需求交付周期 | 比人工基线 -50% | 需求系统 |
| 缺陷密度 | ≤ 人工基线 | 缺陷数 / KLOC |
| AI 代码返工率 | < 15% | PR 二次修改比例 |
| 评审时长 | < 30 min/PR | Git 平台 |
| 测试覆盖率 | 不下降（domain ≥ 80%） | tarpaulin |
| `xtask verify` 通过率 | > 90%（首次） | CI |
| 编译等待时间 | check < 3s | 本地埋点 |

> **反直觉结论**：AI 提效的最大瓶颈通常不是模型能力，而是**编译速度、上下文缺失、验收标准模糊**。这三项都是架构问题，不是 AI 问题。

## 14. 反模式

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 一句话需求让 AI 自由发挥 | 产出不可用，返工 3 次 | 写 20 行 Spec |
| 一次生成 20 个文件不验证 | 错误层层叠加，无法定位 | 小步生成 + 每步 verify |
| 手改生成物 | 下次生成被覆盖 | 改 schema 重新生成 |
| 上下文只给单个文件 | AI 看不到约束，破坏架构 | AGENTS.md + CONTEXT.md |
| 编译 90 秒 | AI 开始"猜" | 拆 crate + lld + sccache |
| 没有测试 | 改 A 坏 B 无人知 | 生成测试骨架 + 覆盖率门禁 |
| 让 AI 改核心事务逻辑 | 数据事故 | 人主导，AI 辅助 |
| 无 ADR 就加依赖 | 供应链风险 + 风格失控 | 依赖白名单 + ADR |
| 用 AI 生成"聪明"的抽象 | 后续谁也改不动 | 显式、直白、重复优于抽象 |

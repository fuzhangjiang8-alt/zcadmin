# 03 · 数据架构

> PostgreSQL 16+｜唯一真相源｜schema-per-plugin + 行级多租户
> 原则：**约束写在库里，规则写在代码里，两者都要有**

---

## 1. 数据域划分

| Schema | 归属 | 内容 | 可写角色 |
|---|---|---|---|
| `sys` | kernel | 用户/角色/菜单/权限/部门/字典/参数/会话/审计/任务/文件元数据 | `app_rw` |
| `plg_{id}` | 插件 | 业务表（如 `plg_crm.customer`） | `app_rw` |
| `rpt` | 报表 | 物化视图、宽表、汇总表 | `report_rw`（只读主库，从库构建） |
| `stage` | 导入 | 临时表、ETL 中间表 | `app_rw` |
| `public` | **禁用** | 不建任何业务表 | — |

```sql
-- 建库时一次完成
CREATE SCHEMA sys;
CREATE SCHEMA plg_crm;
CREATE SCHEMA rpt;
CREATE SCHEMA stage;
REVOKE CREATE ON SCHEMA public FROM PUBLIC;   -- 禁止随手建表
```

**为什么不用 `public`**：所有插件混在一起，表名冲突、权限无法按插件收敛、备份粒度粗、迁移互相阻塞。

## 2. 建模规范

### 2.1 命名

| 对象 | 规则 | 示例 |
|---|---|---|
| 表 | 单数、snake_case、业务前缀省略（靠 schema 区分） | `customer`、`order_item` |
| 列 | snake_case | `created_at`、`credit_limit` |
| 主键 | `id` | — |
| 外键列 | `{引用表单数}_id` | `customer_id` |
| 布尔 | `is_` / `has_` 前缀 | `is_active` |
| 时间 | `_at` 后缀 | `paid_at` |
| 索引 | `idx_{表}_{列...}` | `idx_customer_tenant_status` |
| 唯一约束 | `uq_{表}_{列...}` | `uq_customer_tenant_code` |
| 外键约束 | `fk_{表}_{引用表}` | `fk_order_customer` |

### 2.2 必备列（所有业务表）

```sql
CREATE TABLE plg_crm.customer (
  id           uuid        PRIMARY KEY,                       -- UUIDv7，应用生成
  tenant_id    uuid        NOT NULL REFERENCES sys.tenant(id),
  -- ... 业务列 ...
  version      bigint      NOT NULL DEFAULT 0,                -- 乐观锁
  created_at   timestamptz NOT NULL DEFAULT now(),
  created_by   uuid,
  updated_at   timestamptz,
  updated_by   uuid,
  deleted_at   timestamptz                                    -- 软删
);
```

### 2.3 类型选择

| 场景 | 类型 | 说明 |
|---|---|---|
| 主键 | `uuid`（v7） | 时间有序，索引友好；不用自增（泄漏规模、分库难） |
| 时间 | `timestamptz` | **一律带时区**，禁止 `timestamp` |
| 金额 | `numeric(20,4)` | 禁止 `float`/`double`；Rust 用 `rust_decimal` |
| 枚举 | `text` + `CHECK` | 比 PG enum 易演进（enum 加值需 DDL，且不能在事务外回滚） |
| 短文本 | `varchar(n)` | 有业务上限就加长度，防脏数据 |
| 长文本 | `text` | — |
| JSON | `jsonb` | 仅存"结构不稳定/无需索引"的扩展字段；**禁止当表用** |
| 布尔 | `boolean` | 不用 `char(1)` |
| IP | `inet` | 自带校验与运算符 |
| 哈希/令牌 | `bytea` 或 `text`（hex） | 存哈希不存明文 |

### 2.4 软删的三个坑

| 坑 | 解法 |
|---|---|
| 唯一索引失效（删了还能重复建） | **部分唯一索引**：`CREATE UNIQUE INDEX ... WHERE deleted_at IS NULL` |
| 查询忘记过滤 | 视图封装 + Repository 默认注入；或统一 `active_*` 视图 |
| 数据膨胀 | 定期归档（`deleted_at < now() - interval '1 year'` 物理删除） |

```sql
CREATE UNIQUE INDEX uq_customer_code ON plg_crm.customer (tenant_id, code)
  WHERE deleted_at IS NULL;
```

### 2.5 反范式边界

允许冗余（写明理由）：列表页高频展示的关联名称（`customer_name` 冗余到 `order`）、统计快照（下单时的单价）。
禁止冗余：可变且高频更新的字段（如用户昵称）—— 用 JOIN 或缓存。

## 3. 角色与权限模型

```sql
-- 四类角色，最小权限
CREATE ROLE app_rw   LOGIN PASSWORD '...';   -- 应用读写
CREATE ROLE app_ro   LOGIN PASSWORD '...';   -- 只读（报表/BI）
CREATE ROLE migrator LOGIN PASSWORD '...';   -- 仅迁移期使用
CREATE ROLE backup   LOGIN PASSWORD '...';   -- 备份专用（pg_read_all_data）

GRANT USAGE ON SCHEMA sys, plg_crm TO app_rw;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA sys, plg_crm TO app_rw;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA sys, plg_crm TO app_rw;

-- 插件之间：crm 只能读 sys，不能写
ALTER DEFAULT PRIVILEGES IN SCHEMA sys GRANT SELECT ON TABLES TO app_rw;
-- 本插件 schema 全权限，其他插件 schema 无权限（默认拒绝）

-- 迁移角色：可 DDL，但应用运行时不用它
GRANT ALL ON SCHEMA sys, plg_crm TO migrator;
```

| 规则 | 说明 |
|---|---|
| 应用连接**不是**超级用户 | 防 `DROP TABLE`、防绕过 RLS |
| 迁移用独立连接 | 启动期短连接，用完即关；密码不入配置文件（Vault/K8s Secret） |
| 跨插件只读 | 通过 `GRANT SELECT ON plg_x.v_public_* TO app_rw` 暴露白名单视图 |
| 禁止跨 schema 外键 | 插件解耦；一致性靠事件与对账 |
| `search_path` | 连接串固定 `-c search_path=sys,plg_crm,public`，防注入式覆盖 |

## 4. 索引工程

### 4.1 原则

| 原则 | 说明 |
|---|---|
| 每个查询都有索引支撑 | 上线前 `EXPLAIN (ANALYZE, BUFFERS)` 必看 |
| 复合索引顺序 | 等值列在前，范围列在后，排序列最后 |
| 覆盖索引 | `INCLUDE (col)` 避免回表 |
| 部分索引 | 只索引热数据（`WHERE deleted_at IS NULL`） |
| 表达式索引 | `lower(email)`、`(payload->>'type')` |
| 不建无用索引 | 每个索引都拖慢写入，定期清理 `idx_scan = 0` |

```sql
-- 典型列表查询：tenant + 状态 + 时间倒序
CREATE INDEX idx_customer_list ON plg_crm.customer (tenant_id, status, created_at DESC)
  WHERE deleted_at IS NULL;

-- 模糊搜索：pg_trgm
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_customer_name_trgm ON plg_crm.customer USING gin (name gin_trgm_ops);

-- JSONB 查询
CREATE INDEX idx_order_ext_type ON plg_crm."order" USING gin ((ext->'type'));
```

### 4.2 索引健康检查（每月）

```sql
-- 从未被使用的索引（候选删除）
SELECT schemaname, relname, indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes
WHERE idx_scan = 0 AND indexrelname NOT LIKE '%_pkey'
ORDER BY pg_relation_size(indexrelid) DESC;

-- 重复索引（前缀相同）
SELECT a.indexrelid::regclass AS idx_a, b.indexrelid::regclass AS idx_b
FROM pg_index a JOIN pg_index b
  ON a.indrelid = b.indrelid AND a.indexrelid < b.indexrelid
 AND a.indkey::text LIKE b.indkey::text || '%';
```

### 4.3 CI 查询门禁（可选但强烈建议）

```bash
# 对新增/修改的 SQL 在 staging 副本上跑 EXPLAIN，禁止 Seq Scan（大表）
cargo xtask explain-check --threshold-rows 10000
```

## 5. 分区与大表

### 5.1 必须分区的表

| 表 | 分区键 | 粒度 | 保留 |
|---|---|---|---|
| `sys.audit_log` | `created_at` | 月 | 6 个月热 + 3 年冷（对象存储） |
| `sys.login_log` | `created_at` | 月 | 同上 |
| `sys.outbox` | `created_at` | 周 | 7 天（done 后清理） |
| `sys.job_log` | `created_at` | 月 | 3 个月 |
| 业务流水（订单/操作记录 > 5000 万/年） | 业务时间 | 月 | 按业务 |

```sql
CREATE TABLE sys.audit_log (
  id uuid NOT NULL, tenant_id uuid NOT NULL, created_at timestamptz NOT NULL DEFAULT now(),
  -- ...
) PARTITION BY RANGE (created_at);

CREATE TABLE sys.audit_log_2026_10 PARTITION OF sys.audit_log
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
```

- 用 `pg_partman` 自动建分区与淘汰（或自研 `xtask partition-rotate`，避免额外扩展依赖）。
- **分区裁剪前提**：查询必须带分区键条件，否则全分区扫描。
- 冷数据归档：`COPY (SELECT ...) TO PROGRAM 'aws s3 cp - s3://...'` 或导出 Parquet 后 `DETACH PARTITION` + `DROP`。

### 5.2 大表判定与治理

| 行数 | 状态 | 动作 |
|---|---|---|
| < 100 万 | 正常 | — |
| 100 万–1000 万 | 关注 | 检查索引与慢查询 |
| 1000 万–1 亿 | 警戒 | 评估分区、归档 |
| > 1 亿 | 必须处理 | 分区 / 冷热分离 / 分库 |

## 6. 事务与并发（DBA 视角）

| 项 | 规范 |
|---|---|
| 隔离级别 | 默认 READ COMMITTED；对账用 REPEATABLE READ；强一致用 SERIALIZABLE + 重试 |
| 事务时长 | **< 100ms**，最长不超过 1s；应用侧 `idle_in_transaction_session_timeout` 见第 7 节 |
| 锁顺序 | 多表更新按固定顺序（如按 id 升序），降低死锁概率 |
| 死锁 | 应用层重试 3 次（指数退避）；`deadlock_timeout = 1s` |
| 长事务监控 | `pg_stat_activity` 中 `xact_start` 超 5s 告警 |
| 批量更新 | 分批（每批 1000 行），避免一次性锁全表 |
| 外键 | 高频写入表慎用（每次写入加共享锁），必要时用应用层校验 + 定期对账 |

```sql
-- 长事务巡检
SELECT pid, now() - xact_start AS duration, state, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL AND now() - xact_start > interval '5 seconds'
ORDER BY duration DESC;
```

## 7. 连接管理

| 项 | 规范 | 落地点 |
|---|---|---|
| 单实例池 | 40（见 01 文档公式）；当前默认 20，用 `DB_MAX_CONNECTIONS` 调 | `config/database.max_connections` |
| 最大连接 | `max_connections = 200`（预留 20% 给运维/备份/迁移） | `postgresql.conf` |
| PgBouncer | 应用连接 > 200 时启用，`pool_mode = transaction` | 部署层 |
| 应用侧适配 | `statement_cache_capacity(0)`（transaction 模式下必须） | **未实现**，启用 PgBouncer 前必做 |
| 语句超时 | `statement_timeout = 5s`（报表连接 60s） | `database.statement_timeout_secs`，**每条连接建连时下发** |
| 空闲事务超时 | `idle_in_transaction_session_timeout = max(30s, SQL 超时×6)` | 同上，建连时下发 |
| 连接存活 | `max_lifetime = 30min`、`idle_timeout = 10min` | `database.max_lifetime_secs` |
| 预热 | `min_connections = 5`，启动即建连，避免首请求撞握手 | `database.min_connections` |
| 连接复用 | 禁止在请求外长期持有连接；`pool.acquire()` 作用域尽量小 | 代码评审 |
| 监控 | `pg_stat_activity` 按 state 分组，`wait_event` 分布；应用侧 `db_pool_saturated` | `/metrics` |

> **为什么必须在服务端设超时**：客户端超时（`tokio::time::timeout`、HTTP 断连）只是
> 应用不再等待，PostgreSQL 后端进程仍会继续执行到结束。只有 `statement_timeout`
> 才能真正终止查询、释放 CPU 与锁。这是防雪崩的最后一道闸。
>
> **迁移例外**：`db::run_migrations` 会临时把 `statement_timeout` 设为 0（大表加列/建索引
> 可能超过 5s），并在同一个连接上恢复原值后再归还连接池。

```ini
# postgresql.conf 关键项
max_connections = 200
shared_buffers = 25% RAM
effective_cache_size = 60% RAM
work_mem = 16MB                 # 注意 × 并发数
maintenance_work_mem = 512MB
random_page_cost = 1.1          # SSD
effective_io_concurrency = 200
wal_level = replica
max_wal_size = 4GB
log_min_duration_statement = 500ms
log_lock_waits = on
log_temp_files = 0
```

## 8. 查询规范

| 规范 | 原因 |
|---|---|
| 禁止 `SELECT *` | 加列破坏契约、传输浪费、无法用覆盖索引 |
| 列表必须分页 | 防全表拉取 |
| 禁止在索引列上做函数运算（`where date(created_at)=...`） | 索引失效，改范围查询 |
| 禁止隐式类型转换（`where id = '123'` 而 id 是 int） | 索引失效 |
| `count(*)` 大表用估算 | 全表扫描代价高 |
| 批量 `IN` 控制在 1000 个以内 | 超了改临时表 JOIN |
| 避免 `NOT IN`（含 NULL 陷阱） | 改 `NOT EXISTS` |
| 深分页用游标 | `OFFSET 100000` 扫 10 万行 |
| 排序字段必须有索引 | 否则 `external merge disk` |
| 复杂报表走只读副本 | 不拖垮 OLTP |

```sql
-- 反例
SELECT * FROM plg_crm."order" WHERE to_char(created_at,'YYYY-MM') = '2026-10';
-- 正解
SELECT id, no, amount FROM plg_crm."order"
WHERE created_at >= '2026-10-01' AND created_at < '2026-11-01';
```

**慢查询治理闭环**：`pg_stat_statements` 采集 → 每周 TOP 20 评审 → 加索引/改 SQL/加缓存 → 回归验证。

## 9. 多租户与 RLS

### 9.1 策略模板

```sql
ALTER TABLE plg_crm.customer ENABLE ROW LEVEL SECURITY;
ALTER TABLE plg_crm.customer FORCE ROW LEVEL SECURITY;   -- 表 owner 也受约束

CREATE POLICY tenant_isolation ON plg_crm.customer
  USING (tenant_id = current_setting('app.tenant_id', true)::uuid)
  WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::uuid);
```

| 要点 | 说明 |
|---|---|
| `FORCE` | 防止 owner 绕过（应用若用 owner 连接，不加 FORCE 等于没开） |
| `current_setting(..., true)` | `true` = missing_ok，未设置返回 NULL 而非报错（但会查不到数据，安全侧可接受） |
| 索引 | `tenant_id` 必须是每个索引的最左列，否则 RLS 导致全表扫描 |
| 性能 | 策略表达式要能走索引；避免在策略里调用函数 |
| 测试 | 必须有"跨租户读取返回 0 行"的自动化测试 |

### 9.2 租户生命周期

| 阶段 | 动作 |
|---|---|
| 开通 | 插 `sys.tenant` → 初始化角色/菜单/字典 → 建管理员 → 发通知 |
| 停用 | `status = suspended`，登录拒绝，数据保留 |
| 删除 | 逻辑删除 → 30 天冷静期 → 物理删除（按 schema/租户分批，限速防 IO 打满） |
| 迁移 | 租户数据导出为独立 schema/库（大客户升级路径） |

### 9.3 大租户升级路径

```
行级（默认） → 独立 schema（连接级 search_path） → 独立库（独立实例）
触发条件：单租户占用 > 集群 20% 资源，或有独立备份/合规要求
```

### 9.4 落地进度（2026-11-09 实测）

对真实库执行 `pg_class` 查询的结果，**不是计划表**：

| 状态 | 张数 | 说明 |
|---|---|---|
| `ENABLE` + `FORCE` | **40** | 全部 `sys` 业务表 + CRM 7 张 + demo 1 张 |
| 只 `ENABLE` 未 `FORCE` | **0** | —— |
| 未启用 RLS | **7** | 见下表 |

| 表 | 为什么不启用 RLS |
|---|---|
| `sys_audit_log_202611` / `_202612` / `_202701` / `_default` | 分区子表不单独设策略；访问经父表 `sys_audit_log`（已 FORCE），策略由父表继承 |
| `sys_session` | 登录时先按 `token_hash` 查会话才知道 `tenant_id`，无租户上下文；只按 `token_hash`/`tenant_id` 精确访问 |
| `sys_tenant` | 平台级表，跨租户管理 |
| `sys_permission` | 全局字典，所有租户共享 |

**复核 SQL**（不依赖文档，随时可验证）：

```sql
SELECT n.nspname, c.relname, c.relrowsecurity, c.relforcerowsecurity
FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind='r' AND n.nspname IN ('sys','crm','demo') AND c.relname NOT LIKE '_sqlx%'
ORDER BY 3,4,1,2;
```

期望：只出现 `(true,true)` 与上表 7 张 `(false,false)`。
**任何 `(true,false)` 都是缺陷**——表 owner 可以绕过策略。

**迁移方法**（每一步都可编译、可回滚，新增表必须遵守）：

1. 新增策略但**不加 FORCE**（应用仍可绕过，行为不变）；
2. 把该模块的 handler 从 `state.db` 改为 `TenantTx`（事务内 `SET LOCAL app.tenant_id`）；
3. 回归测试通过后，执行 `ALTER TABLE ... FORCE ROW LEVEL SECURITY`；
4. 观察一周，异常则 `DISABLE` 回滚。

> **新增表必须在同一 PR 内补 FORCE 语句**，否则会重新引入「只 ENABLE」的缺口。
> FORCE 位置参考：内核 `0015_force_rls.sql` / `0022` / `0068` / `0069`，
> CRM `0004_force_rls.sql` / `0018`，demo `0002`。

#### 自动化守护（2026-11 新增）

上面第 3 步「回归测试通过后再 FORCE」靠人记不住，因此加了两道机器检查：

| 层 | 手段 | 失败表现 |
|---|---|---|
| 静态 | `scripts/check-rls-coverage.mjs` | 迁移里「建了策略但没 FORCE」→ `cargo xtask verify` 直接失败 |
| 运行期 | `apps/server/tests/rls_enforced.rs` | 真实库上 **表 owner** 能读到跨租户数据 → 测试失败 |

**为什么运行期一定要用表 owner 测**：

| 角色 | `ENABLE` only | `ENABLE + FORCE` |
|---|---|---|
| 普通角色 | 被拦截 | 被拦截 |
| 表 owner | **绕过** ✅ 能发现问题 | 被拦截 |

只用普通角色测，`ENABLE`-only 的表也会通过——这类测试是假安全的。
生产应用连接通常就是建表角色（`docker-compose.yml` 的 `zcadmin_app` 同时是
database owner 与建表角色），所以 owner 路径才是真实路径。

CI 的 integration job 会创建 `rls_owner`（持有全部 `sys` 表）与 `rls_probe`（普通角色），
两条路径都跑；本地运行方式见 `docs/10-后端代码地图.md` §5.2。

**迁移方法**（每一步都可编译、可回滚）：

1. 新增策略但**不加 FORCE**（应用仍可绕过，行为不变）；
2. 把该模块的 handler 从 `state.db` 改为 `TenantTx`（事务内 `SET LOCAL app.tenant_id`）；
3. 回归测试通过后，执行 `ALTER TABLE ... FORCE ROW LEVEL SECURITY`；
4. 观察一周，异常则 `DISABLE` 回滚。

> 登录已支持租户编码解析；`TenantTx::begin_tenant` 让登录本身也运行在租户事务中。
> `ensure_seed` / `ensure_default_menus` / `sync_plugin_menus` 均已改为「每租户一个事务」。

**FORCE 已由迁移自动启用**（`0015_force_rls.sql` / CRM `0004_force_rls.sql`），
真机冒烟（PostgreSQL 18，全新库 + 存量库）全部通过。

紧急回滚（运维脚本）：

```bash
psql "$DATABASE_URL" -f ops/disable_rls.sql   # 回滚（NO FORCE）
```

## 11. 审计与合规

| 项 | 方案 |
|---|---|
| 应用审计（业务语义） | `sys.audit_log`：who/what/when/before/after/ip/ua/trace_id |
| 数据库审计（DDL/直连） | `pgaudit` 扩展（可选），记录 DDL 与超级用户操作 |

## 12. 报表与分析

| 原则 | 说明 |
|---|---|
| 读写分离 | 报表查询走**只读副本**，不碰主库 |
| 预聚合 | 高频报表用物化视图/汇总表，定时刷新（`REFRESH MATERIALIZED VIEW CONCURRENTLY`） |
| 宽表 | 分析型宽表放 `rpt` schema，由 ETL 任务构建 |
| 大导出 | 异步 + 游标 + 流式写对象存储 |
| 时效 | 明确 T+1 / 准实时（5min）/ 实时（不走报表库） |

```sql
CREATE MATERIALIZED VIEW rpt.mv_customer_monthly AS
SELECT tenant_id, date_trunc('month', created_at) AS month, count(*) AS cnt
FROM plg_crm.customer WHERE deleted_at IS NULL GROUP BY 1,2;
CREATE UNIQUE INDEX ON rpt.mv_customer_monthly (tenant_id, month);  -- 支持 CONCURRENTLY
```

**禁止**：在业务库里跑 `GROUP BY` 全表聚合给前端页面直接调。

## 13. 备份与恢复

| 项 | 方案 |
|---|---|
| 物理备份 | `pgBackRest` 或 `WAL-G`：全量每周 + 增量每日 + WAL 连续归档 |
| 逻辑备份 | `pg_dump -Fc` 每日（小库/迁移用），校验可恢复性 |
| PITR | WAL 归档到对象存储，保留 14 天 → RPO ≤ 5min |
| 恢复演练 | 每季度一次，记录实际 RTO，形成报告 |
| 备份加密 | 服务端加密（SSE-S3/KMS），密钥与备份分离 |
| 异地 | 跨可用区/跨地域复制（SaaS 必备） |
| 验证 | 每周自动 `restore --dry-run` 到临时实例 + `pg_amcheck` |

```bash
# 全量 + WAL 归档
pgbackrest --stanza=main --type=full backup
# PITR 恢复到指定时间点
pgbackrest --stanza=main --type=time --target="2026-10-28 10:00:00+08" restore
```

## 14. 高可用与扩展

| 方案 | 适用 | 说明 |
|---|---|---|
| 流复制（1 主 1 备） | 私有化高可用 | 异步复制，RPO 秒级；切换需人工或 Patroni |
| Patroni + etcd | 自动故障转移 | RTO < 1min，需 VIP/Proxy |
| 同步复制 | 金融级 RPO=0 | 写入延迟上升，至少 1 个同步备 |
| 只读副本 | 报表/导出 | 注意复制延迟（`pg_last_wal_replay_lsn`） |
| 垂直扩容 | 首选 | 加 CPU/内存/IO，PG 对垂直扩展友好 |
| 分区/归档 | 单表过大 | 见第 5 节 |
| Citus | 分片（> 10 亿行/多租户） | 最后手段，运维复杂度高 |

**读副本延迟陷阱**：写后立即读可能读不到 → 关键路径强制走主库（`read_your_writes` 标记），或前端延迟重试。

## 15. 变更管理（DDL 安全）

### 15.1 Expand-Contract 三步法

```
① Expand：加新列（可空/有默认）、加新表、加索引（CONCURRENTLY）→ 发布兼容双写
② Migrate：后台回填数据（分批，限速）→ 校验一致
③ Contract：切换读路径 → 删除旧列/旧表（下一个版本）
```

**禁止**在一个版本里同时"改结构"和"改代码依赖"。

### 15.2 锁风险清单

| 操作 | 锁 | 风险 | 安全做法 |
|---|---|---|---|
| `ADD COLUMN ... DEFAULT` | ACCESS EXCLUSIVE | PG 11+ 常量默认不重写表，但仍需短暂锁 | 低峰执行，设 `lock_timeout` |
| `ALTER COLUMN TYPE` | ACCESS EXCLUSIVE | 全表重写 | 加新列 + 回填 + 切换 |
| `CREATE INDEX` | SHARE | 阻塞写入 | `CONCURRENTLY`（不能事务内） |
| `ADD CONSTRAINT ... FOREIGN KEY` | SHARE ROW EXCLUSIVE | 全表校验 | `NOT VALID` + 后续 `VALIDATE` |
| `VACUUM FULL` | ACCESS EXCLUSIVE | 长时间锁表 | 用 `pg_repack` |
| `DROP COLUMN` | ACCESS EXCLUSIVE | 秒级但需排队 | 设 `lock_timeout = 3s`，失败重试 |

```sql
SET lock_timeout = '3s';
SET statement_timeout = '30s';
```

### 15.3 迁移评审 checklist

- [ ] 是否可重复执行（幂等）？
- [ ] 是否有 `lock_timeout` / `statement_timeout`？
- [ ] 大表操作是否用 `CONCURRENTLY` / 分批？
- [ ] 是否向后兼容（旧代码能跑在新 schema 上）？
- [ ] 回滚方案是什么（是否需要 down 脚本）？
- [ ] 是否影响 RLS 策略与索引？
- [ ] 是否更新了 `sqlx` 离线缓存（`.sqlx/`）？

### 18.1 估算模板

```
单租户年数据量 = 业务单据数 × 平均行宽 × 副本系数(索引 1.5 + TOAST 0.3)
集群容量     = 租户数 × 单租户量 × 增长率 × 安全系数(2.0)

示例：1000 租户 × 50 万单据/年 × 1KB × 1.8 ≈ 900GB/年

```

## 20. 数据层反模式

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 用 `public` 放所有表 | 冲突、权限失控 | schema 分域 |
| 应用用超级用户连库 | RLS 失效、误删库 | 最小权限角色 |
| 软删不加部分唯一索引 | 唯一约束形同虚设 | `WHERE deleted_at IS NULL` |
| 大表 `count(*)` | 页面卡死 | 估算或缓存计数 |
| 在业务库跑报表 | OLTP 抖动 | 只读副本 + 预聚合 |
| 迁移里 `UPDATE` 全表 | 锁表 + WAL 暴涨 | 分批 + 限速 |
| 触发器写业务逻辑 | 隐式、难调试 | 应用层显式处理 |
| `jsonb` 存所有字段 | 无法约束、无法索引 | 结构化列 + 少量扩展 jsonb |
| 索引越多越好 | 写入变慢、膨胀 | 按查询建，定期清理 |
| 备份没演练过 | 真出事恢复不了 | 季度演练 + 自动校验 |

## 11. 索引策略（CRM 补充）

### 11.0 压测结论（5 万回款）

- 列表分页：806 rps，p95 36.5ms —— 分页 + 索引有效；
- 聚合查询：单次 `sum()` 扫 5 万行约 12~18ms，25 并发下 p95 超过 1s；
- 覆盖索引 `INCLUDE (amount_cents)` 仅从 12.6ms 降到 11.6ms，**索引解决不了逐行累加**；
- 结论：聚合瓶颈应通过**预聚合/缓存**解决（合同表冗余 `paid_cents`、按日汇总表），
  而不是无限加索引。

PostgreSQL **不会**为外键自动建索引。CRM 的详情类查询都按外键过滤，缺索引会退化为
「扫描本租户全部行再过滤」：

```sql
-- 0008_crm_fk_indexes.sql
CREATE INDEX idx_contact_customer     ON contact     (tenant_id, customer_id) WHERE deleted_at IS NULL;
CREATE INDEX idx_opportunity_customer ON opportunity (tenant_id, customer_id) WHERE deleted_at IS NULL;
CREATE INDEX idx_contract_customer    ON contract    (tenant_id, customer_id) WHERE deleted_at IS NULL;
CREATE INDEX idx_payment_contract     ON payment     (tenant_id, contract_id) WHERE deleted_at IS NULL;
```

设计要点：

1. **复合索引把 tenant_id 放首位**：RLS 强制带租户条件，单列外键索引几乎用不上；
2. **部分索引**（`WHERE deleted_at IS NULL`）与软删语义一致，索引更小；
3. 验证方式：

```sql
BEGIN;
SELECT set_config('app.tenant_id', '<tenant-uuid>', true);
SET LOCAL enable_seqscan = off;   -- 小数据集下规划器会选 Seq Scan，用这个确认索引可用
EXPLAIN (ANALYZE, BUFFERS) SELECT ... WHERE contract_id = '...';
COMMIT;
```

实测：`idx_payment_contract` 的 Index Cond 同时命中 `tenant_id` 与 `contract_id`。

## 12. 审计日志按月分区

`0021_audit_partition.sql` 把 `sys_audit_log` 改为 `RANGE(created_at)` 分区表：

- 主键 `(id, created_at)`（分区表要求分区键进主键）；
- 迁移时按历史数据范围建月分区，并保留 `sys_audit_log_default` 兜底；
- 索引 `(tenant_id, created_at DESC)`、`(user_id, created_at DESC)` 建在父表；
- RLS 策略与 FORCE 在父表上，自动作用于所有分区。

运行期维护（`audit::ensure_partitions` / `drop_old_partitions`）：

- 启动时补齐未来 2 个月分区；
- 每 24h 检查一次，超过 `audit.retention_days` 的月份直接 `DROP TABLE`（秒级、无膨胀）。

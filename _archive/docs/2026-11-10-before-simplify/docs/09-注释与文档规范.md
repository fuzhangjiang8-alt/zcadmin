# 09 · 注释与文档规范（强制）

> 前提：代码主要由 AI 生成、由人评审、由下一个人（或下一个 AI）继续修改。
> **注释不是"解释代码在做什么"，而是"解释为什么这么做、边界在哪、改坏了会怎样"。**

---

## 0. 一句话原则

```rust
// ❌ 废话注释：把代码翻译一遍
i += 1; // i 加 1

// ✅ 有效注释：解释约束与原因
// 计数器必须在事务提交前递增：失败回滚时依赖它判断是否需要补偿
i += 1;
```

**判断标准**：删掉这行注释，读者会不会做出错误决策？会 → 保留；不会 → 删掉。

---

## 1. 四类必须有注释的位置

| 位置 | 必须写什么 | 缺失后果 |
|---|---|---|
| **文件头**（模块级 `//!` / SFC 块注释） | 职责、边界、关键约束、目录约定 | AI 会往这个文件里塞不该有的逻辑 |
| **公开 API**（`pub fn/struct/enum`） | 做什么、参数含义、失败语义、副作用 | 调用方（人/AI）只能靠猜 |
| **非显然逻辑** | 为什么这样写、替代方案为何不可行 | 后人"优化"掉关键逻辑 |
| **临时方案 / TODO** | 谁、何时、为什么、替代方案 | 临时方案永久化 |

## 2. Rust 规范

### 2.1 文件头（模块文档）

每个 `lib.rs` / `mod.rs` / 主要模块文件顶部必须有 `//!` 块，包含四段：

```rust
//! # 插件注册表
//!
//! 职责：收集编译期注册的插件，做拓扑排序后交给装配器。
//!
//! ## 边界
//! - 不负责执行迁移（由 app::build 负责）
//! - 不感知具体插件类型（只用 trait object）
//!
//! ## 关键约束
//! - 插件 id 必须全局唯一，且只能是小写字母/数字/下划线
//! - 依赖成环时启动失败，不允许"尽力而为"地启动
```

### 2.2 公开项

`#![deny(missing_docs)]` 已强制公开项必须有文档。要求：

```rust
/// 在指定 schema 下执行迁移。
///
/// # 参数
/// - `schema`：目标 schema，必须是合法标识符（只允许小写字母/数字/下划线）
/// - `migrator`：编译期内嵌的迁移集合
///
/// # 失败语义
/// - schema 名非法 → 直接返回错误，不执行任何 SQL
/// - 迁移失败 → 整个启动流程失败（不允许半迁移状态）
///
/// # 副作用
/// 会持有 PostgreSQL 咨询锁，多实例并发启动时只有一个实例真正执行 DDL。
pub async fn run_migrations(...) -> anyhow::Result<()>
```

### 2.3 复杂逻辑

只写"为什么"，不写"是什么"：

```rust
// 为什么用 advisory lock 而不是事务锁：
// DDL 在 PostgreSQL 里可以事务回滚，但多实例并发建表仍会互相阻塞甚至死锁；
// advisory lock 是会话级的，能在整个迁移期间持有，且不需要额外中间件。
let lock_key = advisory_key(schema);

// 为什么这里必须用 true（local）而不是 false：
// set_config(..., false) 会把 tenant_id 写进连接会话，连接被池复用后会串租户 —— P0 级事故。
sqlx::query("SELECT set_config('app.tenant_id', $1, true)")
```

### 2.4 安全性注释

涉及安全边界的地方必须显式标注：

```rust
// SAFETY: 此处无 unsafe（项目全局 forbid(unsafe_code)）。
// SECURITY: 该 SQL 的 schema 名来自内部常量，且经过 validate_identifier 白名单校验；
//           任何来自用户输入的标识符都必须先过同一函数。
```

## 3. 前端（Vue / TS）规范

### 3.1 组件文件头

```vue
<script setup lang="ts">
// =============================================================================
// ProTable —— 管理后台标准列表组件
//
// 职责：查询区 + 工具栏 + 表格 + 分页 的组合封装
// 边界：不做数据请求（由调用方传 request 函数），不做路由跳转
// 约定：
//   - 列配置通过 columns 传入，禁止在组件内写死业务列
//   - 权限过滤依赖 v-perm 指令，不在组件内判断角色
// =============================================================================
</script>
```

### 3.2 类型与接口

```ts
/** 列表查询参数。字段名与后端 OpenAPI 保持一致，禁止自行改名。 */
export interface CustomerQuery {
  /** 页码，从 1 开始 */
  page: number;
  /** 每页条数，后端上限 200 */
  size: number;
  /** 名称模糊搜索，最长 64 字符 */
  keyword?: string;
}
```

### 3.3 模板中的注释

只在"这一段为什么存在"不明显时写：

```vue
<!-- 跨页选择必须保留 rowKey，否则翻页后已选项丢失 -->
<a-table :row-key="rowKey" :preserve-selected-row-keys="true" />
```

## 4. SQL 规范

### 4.1 迁移文件头

```sql
-- =============================================================================
-- 0003_add_customer_credit.sql
--
-- 目的：客户表增加信用额度字段
-- 兼容性：新增可空列，旧代码不受影响（Expand 阶段）
-- 回滚：DROP COLUMN credit_limit（下一版本 Contract 阶段执行）
-- 风险：大表加列在 PG 11+ 不重写表，但仍需短暂 ACCESS EXCLUSIVE 锁
-- =============================================================================
```

### 4.2 表与列注释

```sql
COMMENT ON TABLE plg_crm.customer IS '客户主表：签约主体，租户内 code 唯一';
COMMENT ON COLUMN plg_crm.customer.credit_limit IS '信用额度，单位元，精度 4 位小数';
```

### 4.3 危险操作

```sql
-- ⚠️ 该 UPDATE 会扫描全表（约 2000 万行），必须在低峰期分批执行：
--    WHERE id IN (SELECT id FROM ... LIMIT 1000)
SET lock_timeout = '3s';
```

## 5. TODO 规范

统一格式，便于检索与追责：

```rust
// TODO(M1, 权限中心): 改为从 RBAC 查询权限位图并缓存，预计 2026-Q1 完成。
// 现状：固定返回 ["*"]，仅用于 M0 联调。
```

```ts
// FIXME(前端组, v1.3): 大数据量下会卡顿，等 ProTable 虚拟滚动上线后移除。
```

规则：
- 必须带 **负责人/模块** + **触发条件或版本**；
- 必须说明「现在为什么这样」与「将来怎么改」；
- **禁止**裸 `// TODO`（没有上下文的 TODO 等于垃圾）。

## 6. 禁止事项

| 禁止 | 原因 |
|---|---|
| 注释掉的代码 | 用 Git 历史，不要用注释当版本管理 |
| 过期注释 | 比没有注释更危险（会误导决策） |
| `// 构造函数` 这类翻译式注释 | 零信息量 |
| 大段 ASCII 艺术图 | 维护成本高，改一次就错位 |
| 在注释里写密码/密钥/内网地址 | 安全事故 |
| `#[allow(dead_code)]` 掩盖未使用代码 | 掩盖问题，应删除或加 TODO |
| 用注释解释"为什么编译不过" | 应该修代码 |

---

## 7. 文档与注释的分工

| 内容 | 写在哪 |
|---|---|
| 系统级设计、取舍、ADR | `docs/0X-*.md` |
| 模块职责与边界 | 文件头 `//!` |
| 函数契约与失败语义 | `///` 文档注释 |
| 领域术语 | 插件目录 `CONTEXT.md` |
| 一次性排查记录 | PR 描述 / issue，不进代码 |

---

## 8. 评审清单（Reviewer 用）

- [ ] 新增的公开函数有 `///`，且写清失败语义？
- [ ] 文件头能让人（或 AI）在不看代码的情况下知道这个文件的边界？
- [ ] 非显然的逻辑有"为什么"注释？
- [ ] TODO 有负责人、版本、替代方案？
- [ ] 没有注释掉的代码块？
- [ ] 注释与代码是否同步（改了行为没改注释）？
- [ ] SQL 迁移有目的/兼容性/回滚/风险四段说明？

---

## 9. 对 AI 的特别要求

AI 生成代码时必须：

1. **先写文件头**，再写实现 —— 这相当于强制它先想清楚职责边界。
2. **每个 `pub` 项必须写文档注释**，编译器会检查（`deny(missing_docs)`）。
3. **不要用注释复述代码**，把注释预算花在"约束、原因、坑"上。
4. **改动行为时同步改注释**，否则视为未完成（DoD 的一部分）。
5. **不确定的地方写 `// 待确认:` 并在 PR 里提问**，不要用注释假装确定。

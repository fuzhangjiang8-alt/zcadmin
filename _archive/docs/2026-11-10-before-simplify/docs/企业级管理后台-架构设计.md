## 1. 业务范围

对标若依（RuoYi-Vue）的能力域，并补上若依缺的企业级部分：

| 域 | 若依已有 | 本方案增强 |
|---|---|---|
| 组织与权限 | 用户/角色/菜单/部门/岗位、数据范围 | 权限点由插件自声明并自动入库、字段级脱敏、对象级授权（防 IDOR） |
| 系统配置 | 字典/参数/公告 | 配置版本化 + 灰度生效 + 变更审计 |
| 审计 | 操作日志/登录日志 | 事务性 outbox 异步落库、按月分区、留存策略、WORM 归档 |
| 任务 | Quartz 定时任务 | apalis + PG 队列、分布式锁、重试退避、执行链路追踪 |
| 文件 | 本地/OSS | `object_store` 抽象、预签名直传、分片续传、配额与病毒扫描钩子 |
| 代码生成 | 单表/树表 CRUD | `xtask gen-crud` 生成后端四层 + 前端页面 + 迁移 + 权限点 + 测试骨架 |
| 多租户 | 无（需二开） | 行级 RLS 默认，schema/独立库平滑升级 |
| 工作流 | Flowable 集成 | 轻量状态机内置；复杂 BPMN 外挂 Temporal/Flowable（不自研） |
| 可观测 | 无 | OTel 全链路 + Prometheus + 结构化日志 + 审计三件套 |
| 插件化 | 无 | crate 级插件 + 契约 + 装配器 + 前端插件包 |

**明确不做**（首两年）：自研 BPMN 引擎、自研报表引擎、自研消息中间件、dylib 热插拔。

## 2. 非功能需求（NFR）

架构的第一性约束。任何设计取舍以本表为准，冲突时按 **安全 > 正确性 > 可用性 > 性能 > 开发效率** 排序。

| 维度 | 目标值 | 验证方式 |
|---|---|---|
| 并发 | 500 在线操作员，峰值 1000 QPS（读 8 : 写 2） | 压测（k6）+ 生产监控 |
| 延迟 | 列表/详情 P95 < 200ms、P99 < 500ms；聚合报表走异步 | 压测 + APM |
| 首屏 | 内网 < 1.5s，路由切换 < 300ms | Lighthouse CI + RUM |
| 可用性 | 单机房 99.9%；主备 99.95%（年停机 ≤ 4.4h） | 月度统计 |
| 数据可靠性 | **RPO ≤ 5min，RTO ≤ 30min** | 每季度恢复演练 |
| 数据规模 | 单业务表 ≤ 1 亿行；审计表按月分区，年增 ≤ 5 亿行 | 容量模型 + 监控 |
| 租户规模 | 单集群 ≤ 1000 租户，单租户 ≤ 5 万用户 | 压测 |
| 审计留存 | 登录/操作日志 ≥ 6 个月（等保三级），可归档至对象存储 3 年 | 策略校验 |
| 发布 | 不停机，灰度 10% → 50% → 100%，5 分钟内可回滚 | 发布演练 |
| 安全 | 等保三级基线；OWASP Top 10 全覆盖 | 渗透测试 + 代码审计 |
| 兼容 | 后端 N-1 版本 API 兼容 ≥ 6 个月；前端支持 Chrome/Edge 最近 2 个大版本 | 契约快照 + CI |
| 可维护 | 单插件 ≤ 3 万行；新增插件不改内核代码 | 架构守护测试 |

> **容量反推示例**：1000 QPS × 平均 3 条 SQL × 5ms = 15 个活跃连接；按 4 倍余量 + 后台任务 → 单实例池 40，PgBouncer 前端 200。详见 `03-数据架构.md` 第 7 节。

### 2.1 目标 vs 现状（不要混读）

上表是**架构目标**，不是当前实测结论。截至 2026-11：

| 维度 | 状态 | 说明 |
|---|---|---|
| 并发 / 延迟 | ⚠️ **未验证** | 现有基线是 25 并发、单机、`oneshot`（不经 TCP），见 README「性能基线」 |
| 过载行为 | ✅ 已实现 | 并发上限 + 连接池 acquire 超时 + 阻塞池限流，统一返回 503 + `Retry-After` |
| 发布不停机 | ⚠️ 部分 | 优雅停机已实现（摘流 → 排空 20s → 关池 → flush）；灰度与 5 分钟回滚属部署层，未演练 |
| 安全基线 | ⚠️ 部分 | 等保要求的多项（MFA、双令牌、空闲超时）未实现，见 `05` 文档 |
| 数据可靠性 | ⚠️ 未演练 | 备份/恢复脚本与 RPO/RTO 需实际演练后才有结论 |

> 目标值变更必须评审；「未验证」项在没有压测/演练数据前，不得对外宣称已达成。

## 3. 质量属性 → 架构策略

| 质量属性 | 威胁场景 | 架构策略 |
|---|---|---|
| 性能 | 列表页 N+1、报表拖垮 OLTP | 强制分页、Repository 单查询聚合、报表走只读副本、慢查询门禁 |
| 可用性 | 单点故障、发布引入缺陷 | 无状态应用 + 多副本、灰度发布、熔断降级、健康检查 |
| 安全 | 越权、注入、会话劫持 | RLS 兜底 + 应用层校验、sqlx 绑定参数、HttpOnly Cookie + CSRF |
| 可维护 | 插件腐化、边界侵蚀 | crate 边界 + 依赖方向检查 + 契约测试 + CODEOWNERS |
| 可扩展 | 新业务必须改内核 | 插件 trait + 装配器 + 权限/菜单/字典自声明 |
| 可观测 | 线上问题无法定位 | trace_id 全链路透传 + 结构化日志 + RED 指标 |
| 可移植 | 客户私有化环境差异 | 单二进制 + 配置分层 + 仅依赖 PG（Redis/MinIO 可选） |

## 4. 总体架构

### 4.1 逻辑架构

```
┌─────────────────────────────────────────────────────────────┐
│ 表现层  Vue3 SPA（admin-web + 插件前端包，构建期聚合）        │
└───────────────────────────┬─────────────────────────────────┘
                            │ HTTPS / HttpOnly Cookie + CSRF
┌───────────────────────────▼─────────────────────────────────┐
│ 接入层  Nginx / Ingress（TLS、静态资源、压缩、限流兜底）      │
└───────────────────────────┬─────────────────────────────────┘
┌───────────────────────────▼─────────────────────────────────┐
│ 应用层  axum（无状态，可水平扩展）                            │
│  ┌───────────────────────────────────────────────────────┐  │
│  │ 中间件链：trace → recover → security-headers → csrf   │  │
│  │           → auth → tenant → rls → rbac → ratelimit    │  │
│  │           → audit → timeout                           │  │
│  └───────────────────────────────────────────────────────┘  │
│  ┌──────────────┐  ┌────────────────────────────────────┐   │
│  │ kernel（sys）│  │ PluginRegistry（inventory 注册）    │   │
│  │ auth/rbac    │  │ crm │ wms │ oa │ report │ ...      │   │
│  │ menu/dict    │  └────────────────────────────────────┘   │
│  │ audit/job    │                                           │
│  │ event/file   │                                           │
│  └──────────────┘                                           │
└───────┬──────────────┬──────────────┬───────────────────────┘
        │              │              │
   ┌────▼────┐   ┌─────▼─────┐  ┌─────▼──────┐
   │ PG 16+  │   │ Redis 7   │  │ S3/MinIO   │
   │ 唯一真相│   │ 缓存/锁   │  │ 文件/归档  │
   │ 源      │   │ （可选）  │  │ （可选）   │
   └─────────┘   └───────────┘  └────────────┘
```

**原则**：PG 是唯一真相源；Redis 与对象存储均为**可降级**组件，缺失时功能受限但不崩溃。

### 4.2 部署形态

| 形态 | 拓扑 | 适用 | 关键差异 |
|---|---|---|---|
| **私有化单机** | 1 app + 1 PG（+ 可选 MinIO） | 中小客户、内网 | 单二进制 + docker compose，5 分钟交付 |
| **私有化高可用** | 2 app + PG 主备（Patroni）+ VIP | 大型客户 | 无状态双活，DB 切换 RTO < 1min |
| **SaaS 多租户** | N app + PgBouncer + PG 主从 + Redis + 对象存储 | 自营 | 行级租户隔离、按租户限流与配额 |

### 4.3 运行时视图（一次写请求）

```
Vue → Nginx → axum
  ├ 生成 trace_id，写入 response header 与日志上下文
  ├ 解析 Cookie → 会话校验 → Principal
  ├ 解析 tenant（JWT claim / 子域） → TenantCtx
  ├ 开启事务 → SET LOCAL app.tenant_id / app.user_id（RLS 生效）
  ├ 路由匹配 → 权限点校验（缓存命中 < 1μs）
  ├ handler：DTO 校验 → service（业务规则）→ repo（SQL）
  ├ 写 outbox（同事务）→ COMMIT
  ├ 异步派发器消费 outbox → 插件订阅者 / 缓存失效
  └ 审计中间件落审计记录（异步），返回 200 + trace_id
```

## 5. 分层与依赖规则

```
apps/server ──▶ plugins/* ──▶ kernel ──▶ (外部 crate)
                   │            ▲
                   └────────────┘  仅允许 plugins 依赖 kernel；禁止 kernel 反向依赖 plugin
```

| 规则 | 说明 | 强制手段 |
|---|---|---|
| R1 | `kernel` 不得依赖任何 `plugin` | Cargo 依赖图 + `cargo xtask arch-check` |
| R2 | 插件之间不得直接依赖（`crm` 不能 `use wms::…`） | 同上 + CI 校验 |
| R3 | 插件间通信只能走领域事件或公共 `contract` crate | 评审 + clippy lint |
| R4 | handler 不得直接写 SQL，repo 不得做业务判断 | 评审 checklist |
| R5 | 跨插件读数据必须通过只读视图或对方 API | DB role 权限限制 |
| R6 | 前端包之间不得互相 import，只能依赖 `@admin/sdk`、`@admin/ui` | eslint-plugin-boundaries |

> R1/R2 用 `cargo metadata` 解析依赖图，在 `xtask arch-check` 中断言并进 CI。**架构规则不靠自觉，靠流水线。**

## 7. 关键架构决策（ADR 摘要）

| 编号 | 决策 | 理由 | 代价 | 复审触发条件 |
|---|---|---|---|---|
| ADR-001 | 模块化单体，非微服务 | 管理后台低 QPS 高复杂度，事务与调试成本优先 | 单进程故障域大 | 插件资源画像显著不同或团队 > 3 组 |
| ADR-002 | 插件 = crate + trait + inventory | Rust 无稳定 ABI，dylib 不安全 | 插件升级需重新发布 | 需客户现场热装 → MF / WASM |
| ADR-003 | 每插件独立 PG schema | 隔离迁移与表名，卸载干净 | 跨插件联表成本高 | 出现高频跨域查询 → 宽表/视图 |
| ADR-004 | HttpOnly Cookie 会话 | XSS 无法直接窃取令牌 | 需 CSRF 防护，跨域配置复杂 | 纯 API 客户端 → 增加 Bearer 模式 |
| ADR-005 | 行级多租户 + RLS | 单库成本低、隔离可验证 | 大租户 noisy neighbor | 单租户 > 集群 20% 资源 → 独立 schema |
| ADR-006 | 事务性 outbox 做事件 | 业务落库与事件发出原子 | 派发延迟（秒级） | 需强实时 → 评估 CDC |
| ADR-007 | OpenAPI 为前后端唯一契约 | 消除手抄字段与漂移 | 注解质量要求高 | — |
| ADR-008 | 前端插件构建期聚合，MF 为演进 | 类型安全、调试简单 | 无法热插拔 | 客户现场装插件 |
| ADR-009 | 不自研 BPMN | 无底洞 | 复杂流程需外挂 | 单流程 > 20 个审批节点 |
| [ADR-0004](adr/0004-panic-unwind与请求级隔离.md) | panic = unwind + 请求级隔离 | 单请求 bug 不再拖垮整个实例 | 二进制略大 | 追求极致体积的嵌入式场景 |
| [ADR-0005](adr/0005-受控阻塞池.md) | Argon2/xlsx 走**限流**阻塞池 | 防止 worker 与内存被打爆 | 过载时返回 503 | 引入独立哈希服务 |
| [ADR-0006](adr/0006-客户端IP只信TCP对端与可信代理.md) | 只信 TCP 对端，转发头需显式白名单 | IP 不可伪造，审计可信 | 网关后必须配置 | 全站直连（无代理） |
| ADR-010 | 单二进制 + rust-embed 交付 | 私有化部署极简 | 包体增大（~40MB） | SPA 独立 CDN 交付 |
| ADR-011 | 不用 DI 框架，组合根 + Arc | 减少魔法，编译期可查 | 手工装配样板 | 插件依赖数 > 50 |
| ADR-012 | 全链路 UUIDv7 主键 | 时间有序、分布式友好、不泄漏规模 | 存储 16B vs 8B | 极端写入量场景复评 |
| ADR-013 | 扩展模型分三级（crate / 服务 / UI） | 业务型插件轻量，通信型/智能型必须独立部署 | 需维护能力注册中心 | 服务数 > 20 时引入服务网格 |
| ADR-014 | 以 CloudEvents 为跨产品事件契约 | 跨语言、可重放、可审计 | 需要 Schema Registry | 事件量 > 10 万/秒 |
| ADR-015 | 数据"能放 PG 就放 PG" | 每多一种存储 +1 套备份/监控/技能 | 极端量级需迁移 | 单表 > 1 亿或写入 > 5000 TPS |
| ADR-016 | 允许 Python 承担 AI 推理 | 生态无可替代，Rust 重写不现实 | 多语言运维成本 | 出现统一推理框架且 Rust 生态成熟 |
| ADR-017 | 前端 Ant Design Vue 4 + 自研薄壳 | 组件最全、类型完整、语料多；Vben 抽象层厚对 AI 不友好 | 壳需自研（约 3000 行） | 组件库停止维护或团队强偏好 Element Plus |
| ADR-018 | Schema 驱动 + 生成器优先 | AI 开发下"确定性"比"灵活性"更值钱 | 生成器本身需要维护 | DSL 表达不了复杂业务时，改为生成 + 手写混合 |
| ADR-019 | 桌面端 Tauri 2 + 复用 Web 前端 | 包体 5–15MB、内存约为 Electron 的 1/3，Rust 团队可维护壳层 | WebView 内核不一致，需三平台冒烟 | Linux 必须支持且 WebKitGTK 不可用时 |
| ADR-020 | 移动端 Flutter 独立实现 | 国产 ROM 后台保活/厂商推送/原生能力，Web 方案不可行 | UI 需独立维护一套 | 移动端只做只读展示（可改用 H5） |

## 8. 环境矩阵

| 环境 | 数据 | 用途 | 门禁 |
|---|---|---|---|
| local | docker compose，种子数据 | 开发 | fmt + clippy + 单测 |
| ci | 临时 PG 容器 | 流水线 | 全量测试 + 契约快照 + `sqlx prepare --check` |
| test | 脱敏小数据集（10 万行级） | 联调 / QA | 集成测试 + E2E |
| staging | 生产同构，1/10 数据 | 预发 / 压测 / UAT | 性能基线 + 安全扫描 |
| prod | 生产 | — | 灰度 + 回滚预案 |

**铁律**：禁止本地直连生产库；生产变更必须走流水线；生产数据导出必须脱敏。

## 9. 演进路线与团队分工

| 阶段 | 周期 | 交付 | 出口标准 |
|---|---|---|---|
| M0 骨架 | 2–3 周 | workspace、kernel 基础、健康检查、登录闭环、CI | 一条命令起环境并登录 |
| M1 系统管理 | 3–4 周 | RBAC 全链路、菜单、字典、审计、数据权限 | 对标若依系统模块可用 |
| M2 插件体系 | 2–3 周 | 契约 + 装配器 + `new-plugin` + demo 插件 + 前端聚合 | 新插件不改内核跑通 CRUD |
| M3 生产力 | 3 周 | `gen-crud`、文件、任务、通知、导入导出 | 新表 10 分钟出全套 CRUD |
| M4 企业化 | 3–4 周 | 多租户 RLS、OTel、压测、灰度发布、备份演练 | 500 并发 P95 < 200ms |
| M5 生态 | 持续 | 插件注册表、版本矩阵、开发者文档 | 第三方可独立交付插件 |

**团队分工（CODEOWNERS）**

| 目录 | Owner | 职责 |
|---|---|---|
| `crates/kernel` | 平台组 | 契约、横切、稳定性；变更需架构评审 |
| `plugins/*` | 各业务组 | 独立发布，遵守契约与迁移规范 |
| `apps/admin-web`、`packages/*` | 前端组 | 框架与组件资产 |
| `plugins-web/*` | 业务组前端 | 与后端插件同版本号 |
| `deploy/`、CI 配置 | DevOps | 流水线、镜像、发布 |

## 10. 术语表

| 术语 | 含义 |
|---|---|
| 内核（kernel） | 提供契约、装配、系统管理与横切能力的固定部分，业务团队不修改 |
| 插件（plugin） | 独立 crate，实现 `Plugin` trait，承载一个业务域 |
| 权限点 | `{plugin}:{resource}:{action}` 三元组，最小授权单元 |
| 数据范围 | 行级可见性规则（全部/部门/部门及以下/本人/自定义） |
| Outbox | 与业务同事务写入的事件表，由派发器异步消费 |
| 装配器（AppBuilder） | 遍历插件注册表，完成迁移、种子、路由挂载的组件 |
| RLS | PostgreSQL 行级安全策略（Row Level Security） |

# 企业级管理后台技术架构（Rust axum + sqlx + Vue3）

> 对标：若依（RuoYi-Vue）功能域｜形态：模块化单体 + 插件化｜目标：多团队长期并行维护插件

---

## 1. 目标与硬约束

| 项 | 取值 |
|---|---|
| 后端 | Rust 1.8x + axum 0.8 + sqlx 0.8（PostgreSQL 15+） |
| 前端 | Vue 3 + Vite + TypeScript + Pinia + Element Plus（或 Naive UI） |
| 形态 | **单二进制交付**，插件编译期内嵌；预留"远程插件"模式 |
| 组织 | 内核 1 个团队长期维护；每个业务插件独立仓库/独立发布节奏 |
| 非目标 | 不做 dylib 热插拔、不首期上微服务、不自研 BPMN 引擎 |

## 2. 六个核心决策（先看这个，其余都是细节）

### 决策一：**模块化单体，不是微服务**

一个二进制 + 一个 PG 库，靠 **crate 边界**强制模块隔离。理由：

- 管理后台的流量特征是"低 QPS、高复杂度"，微服务只会把事务一致性、链路追踪、部署成本全部放大。
- 拆服务的时机判据（满足任一再说）：① 某插件的资源画像显著不同（CPU/内存/IO 尖峰）；② 某插件需要独立扩缩容或独立合规边界；③ 团队规模 > 3 个小组且发布互相阻塞。
- 本架构天然支持平滑演进：插件路由既可内嵌也可反向代理到独立进程（见决策三），**代码不改，只改装配**。

### 决策二：**插件 = crate + trait 契约 + inventory 注册**

Rust 没有稳定 ABI，**dylib 动态加载是坑**（`abi_stable` 限制多、跨 crate 版本类型不兼容、tokio 任务无法安全卸载）。正确做法：

- 每个插件是一个独立 crate（可独立仓库，通过 git 依赖或私有 registry 引入）。
- 插件实现统一 `Plugin` trait，用 `inventory` 在链接期自动注册。
- 内核遍历注册表完成：迁移执行 → 权限点 upsert → 菜单注册 → 路由挂载 → 任务注册 → 事件订阅。
- **新增插件 = 新建 crate + 在 `apps/server/Cargo.toml` 加一行依赖，内核零改动。**

### 决策三：**三种插件形态，按信任级别选**

| 形态 | 适用 | 隔离性 | 热更新 | 建议 |
|---|---|---|---|---|
| **A. 编译期内嵌 crate** | 自有团队的核心业务插件 | 进程内，无隔离 | 需重新发布 | **默认，90% 场景** |
| B. WASM 组件（wasmtime + component model） | 三方/不可信扩展、规则钩子、数据转换 | 沙箱 | 支持 | 只做"钩子"，不适合整块 CRUD |
| C. 独立服务（gRPC/HTTP） | 异构语言、独立扩容、遗留系统接入 | 进程级 | 支持 | 网关转发 `/api/{id}/*`，配置开关 |

> 关键设计：同一个插件 crate 既可以被 `apps/server` 内嵌，也可以加一个 `bin/` 单独编译成服务，路由层代码完全复用。这就是"同构单体/微服务双形态"。

### 决策四：**数据库按插件分 schema，迁移各自独立**

- 内核：`sys` schema（用户/角色/菜单/权限/字典/参数/日志/任务/租户）。
- 插件：`plg_{id}` schema（如 `plg_crm`），插件只写自己的 schema，**读 `sys` 允许，写 `sys` 禁止**（DB 权限层面用 role 限制）。
- 迁移：每个插件自带 `migrations/` 目录，用 `sqlx::migrate!()` 编译期内嵌；执行前 `SET search_path = plg_x`，`_sqlx_migrations` 自然隔离在各 schema 内。
- 好处：插件卸载 = drop schema；插件间零表名冲突；迁移顺序可追溯。
- 代价：跨插件联表变麻烦 → 用视图或 qualified name，禁止跨 schema 外键。

### 决策五：**认证用 HttpOnly Cookie + CSRF，不用 localStorage JWT**

管理后台是浏览器场景，localStorage 存 token 等于把 XSS 变成账号接管。方案：

- 登录成功 → `Set-Cookie: access_token`（HttpOnly + Secure + SameSite=Lax，15min）+ `refresh_token`（HttpOnly，7d，服务端可撤销）。
- 双提交 CSRF：非 GET 请求校验 `X-CSRF-Token` 头与 cookie 内的 token 一致。
- 授权：RBAC 权限点 `{plugin}:{resource}:{action}`，插件自声明、框架自动入库、超管自动授权。
- 数据权限（若依的"数据范围"）：`全部/本部门/本部门及以下/仅本人/自定义`，在 Repository 层用 `sea-query` 组合 `WHERE` 条件并绑定参数，**禁止字符串拼接**。

### 决策六：**前端也插件化，构建期聚合，运行期按需升级**

- pnpm workspace：`apps/admin-web` + `packages/*` + `plugins/*-web`。
- 每个前端插件导出 `plugin.ts` 清单（路由、组件、权限点、菜单补充）。
- 用 `import.meta.glob('../../plugins/*/plugin.ts', { eager: true })` 在构建期聚合 → 类型安全、可按插件做 chunk 分包。
- 需要"客户现场装插件"时，再引入 **Module Federation（@module-federation/vite）** 运行时加载，接口不变。
- 菜单/按钮权限全部**后端下发**，前端只维护"组件路径 → 组件"的映射表，避免前后端菜单两处维护。

## 5. 插件契约（核心代码）

```rust
// crates/kernel/src/plugin.rs
use axum::Router;
use std::future::Future;
use std::pin::Pin;

pub type BoxFuture<T> = Pin<Box<dyn Future<Output = T> + Send + 'static>>;

#[derive(Clone, Copy, Debug)]
pub struct PluginMeta {
    pub id: &'static str,              // "crm"：路由前缀 + schema 名 + 权限点前缀
    pub name: &'static str,
    pub version: &'static str,         // 与 Cargo.toml 同步（build.rs 注入）
    pub depends_on: &'static [&'static str],
    pub order: i32,                    // 同层装配顺序
}

pub struct PluginCtx {
    pub db: sqlx::PgPool,
    pub events: EventBus,
    pub cfg: Arc<Config>,
    pub storage: Arc<dyn ObjectStore>,
}

pub trait Plugin: Send + Sync + 'static {
    fn meta(&self) -> PluginMeta;

    /// 插件迁移（框架负责先建 schema，再 SET search_path 执行）
    fn migrations(&self) -> &'static [Migration] { &[] }

    /// 挂在 /api/{id} 下；返回的路由已带 AppState
    fn routes(&self) -> Router<AppState> { Router::new() }

    /// 权限点声明 → 自动 upsert 到 sys_permission，超管自动授权
    fn permissions(&self) -> Vec<PermissionDef> { Vec::new() }

    /// 菜单/按钮声明 → 前端动态路由的唯一来源
    fn menus(&self) -> Vec<MenuDef> { Vec::new() }

    /// 字典类型/字典项 → 自动入库，前端按 type 取
    fn dicts(&self) -> Vec<DictDef> { Vec::new() }

    /// 定时任务声明 → 写入 sys_job，由统一调度器按 cron 触发
    fn jobs(&self) -> Vec<JobDef> { Vec::new() }

    /// 领域事件订阅 → outbox 派发
    fn subscribers(&self) -> Vec<Box<dyn EventSubscriber>> { Vec::new() }

    /// 启动钩子（缓存预热、外部连接建立）
    fn on_start<'a>(&'a self, _ctx: &'a PluginCtx) -> BoxFuture<anyhow::Result<()>> {
        Box::pin(async { Ok(()) })
    }
}

inventory::collect!(&'static dyn Plugin);
```

```rust
// plugins/crm/src/lib.rs
pub struct CrmPlugin;

impl Plugin for CrmPlugin {
    fn meta(&self) -> PluginMeta {
        PluginMeta { id: "crm", name: "客户管理", version: env!("CARGO_PKG_VERSION"),
                     depends_on: &["system"], order: 100 }
    }
    fn routes(&self) -> Router<AppState> {
        Router::new()
            .route("/customers", get(api::customer::list).post(api::customer::create))
            .route("/customers/{id}", get(api::customer::get).patch(api::customer::update))
    }
    fn permissions(&self) -> Vec<PermissionDef> {
        perms!["crm:customer:list" => "客户查询", "crm:customer:add" => "客户新增"]
    }
}

inventory::submit! { &CrmPlugin as &'static dyn Plugin }
```

```rust
// crates/kernel/src/app.rs —— 装配
pub fn build(cfg: Config) -> anyhow::Result<Router> {
    let mut plugins: Vec<&'static dyn Plugin> =
        inventory::iter::<&'static dyn Plugin>.into_iter().copied().collect();
    plugins.sort_by_key(|p| (p.meta().order, p.meta().id));
    assert_topological(&plugins);            // 校验 depends_on 存在且无环

    let mut app = Router::new();
    for p in &plugins {
        p.migrate(&pool)?;                   // 建 schema + 跑迁移
        p.sync_seeds(&pool)?;                // 权限点/菜单/字典/任务 upsert
        app = app.nest(&format!("/api/{}", p.meta().id), p.routes());
    }
    Ok(app.layer(middleware_stack()).with_state(state))
}
```

**插件作者的心智负担**：`use kernel::prelude::*;` → 实现 trait → 提交注册。不需要懂装配、不需要碰 `main.rs`。

## 6. 数据层规范

### 6.1 统一表约定

```sql
-- 所有业务表必备列
id           uuid primary key,                 -- UUIDv7（时间有序，B-tree 友好）
tenant_id    uuid not null,                    -- 多租户；单租户部署填默认值
created_at   timestamptz not null default now(),
created_by    uuid,
updated_at   timestamptz,
updated_by    uuid,
deleted_at    timestamptz,                     -- 软删
version      bigint not null default 0         -- 乐观锁
```

- 主键用 **UUIDv7**（`uuid::Uuid::now_v7()`），避免自增 ID 泄漏规模、避免随机 UUID 的索引碎片。
- 软删统一 `deleted_at IS NULL`，通过视图或 Repository 默认条件注入，禁止各写各的。
- 枚举用 `text + check` 或 PG enum；金额用 `numeric(20,4)` + Rust `rust_decimal`。

### 6.2 迁移

- `sqlx::migrate!("./migrations")` 编译期校验，**迁移文件不可修改**，只能追加。
- 每插件独立 schema → 独立 `_sqlx_migrations`，插件卸载/回滚简单。
- CI 里跑 `cargo sqlx prepare` 生成 `.sqlx/` 离线缓存，保证无库也能编译。
- 向后兼容原则：加列可空 → 双写 → 回填 → 加约束，三步发版。

### 6.3 多租户

| 模式 | 适用 | 实现 |
|---|---|---|
| **行级 + RLS（默认）** | 绝大多数 SaaS | 每表 `tenant_id` + PG RLS 策略读 `current_setting('app.tenant_id')` |
| schema-per-tenant | 大客户/强隔离/独立备份 | 连接时 `search_path=tenant_x`，框架层切换 |
| 独立库 | 私有化交付 | 配置切换数据源 |

RLS 落地要点：

```rust
// 每请求在事务内设置，事务结束自动失效
sqlx::query("SELECT set_config('app.tenant_id', $1, true)")
    .bind(tenant_id.to_string()).execute(&mut *tx).await?;
```

```sql
CREATE POLICY tenant_isolation ON plg_crm.customer
  USING (tenant_id = current_setting('app.tenant_id', true)::uuid);
```

> 应用层过滤 + RLS 双保险：应用层给正确结果，RLS 兜底防漏。别只依赖一层。

### 6.4 数据权限（对标若依）

```rust
pub enum DataScope { All, Dept, DeptAndChild, SelfOnly, Custom(Vec<Uuid>) }

// Repository 层组合条件，全部走绑定参数
let mut q = Query::select().from(Customer::Table).and_where(Expr::col(Customer::DeletedAt).is_null());
match scope {
    DataScope::SelfOnly => { q.and_where(Expr::col(Customer::CreatedBy).eq(user_id)); }
    DataScope::DeptAndChild => { q.and_where(Expr::col(Customer::DeptId).is_in(dept_ids)); }
    DataScope::All => {}
    ...
}
```

## 7. 认证与权限

```
登录 → 校验密码(argon2id) → 建会话(Redis/DB) + 下发 access/refresh cookie
     → 返回用户信息 + 权限点集合 + 菜单树
请求 → 中间件：解 cookie → 校验签名/过期 → 载入 Principal
     → 提取 tenant_id → SET LOCAL app.tenant_id
     → 路由级 layer: require_perm!("crm:customer:add")
```

- 密码哈希：**argon2id**（不是 bcrypt/md5，若依老版本用 bcrypt，Rust 侧直接用 argon2）。
- 会话可撤销：refresh token 存 `sys_session`，支持"踢下线"、单点登录限制。
- 权限点命名统一 `{plugin}:{resource}:{action}`，与前端 `v-perm="'crm:customer:add'"` 一一对应。
- 超管走 `is_super` 短路，但**仍然记审计日志**。
- 接口级限流：登录/验证码/导出 单独更严的桶（`tower_governor`）。

const modules = import.meta.glob('../../../../plugins-web/*/plugin.ts', { eager: true });
export const plugins = Object.values(modules).map((m: any) => m.default);

- 演进：客户现场需要独立发布前端插件时，把 `plugin.ts` 换成 Module Federation 的 `exposes`，宿主侧改成远程加载，**接口零改动**。

## 9. 横切能力（内核提供，插件白嫖）

| 能力 | 实现 | 说明 |
|---|---|---|
| 统一响应 | `ApiResult<T>` + RFC 9457 `problem+json` | 错误码 `{plugin}.{code}`，前端统一拦截 |
| 错误 | `thiserror` 领域错误 + `AppError` 映射 | 禁止 `anyhow` 泄漏到 handler 返回值 |
| 日志/追踪 | `tracing` + `tracing-opentelemetry` | 每请求一个 trace_id，回传给前端便于排障 |
| 审计 | 中间件 + outbox 表异步落库 | 记录 who/what/when/before/after |
| 领域事件 | 进程内 `broadcast` + 事务性 outbox | 插件间解耦，禁止跨插件直接调 service |
| 定时任务 | `apalis` + PG 后端 + `sys_job` 表 | 支持 cron、手动触发、执行日志、失败重试 |
| 缓存 | `moka`（本地）+ Redis（分布式，可选） | 两级缓存，字典/参数走本地 |
| 文件 | `object_store` 抽象（S3/MinIO/本地） | 预签名 URL，后端不代理大文件流 |
| 通知 | `notify` 插件：站内信/邮件/Webhook | 模板 + 渠道适配器 |
| 导入导出 | `calamine` 读 / `rust_xlsxwriter` 写 | 大数据量走异步任务 + 下载中心 |
| 限流 | `tower_governor` | 分接口配置 |

## 10. 工程效率（决定"能不能长期维护"的关键）

1. **`cargo xtask new-plugin <id>`** —— 一键生成：Cargo.toml、lib.rs 骨架、migrations 目录、权限点占位、前端 `plugin.ts` + 示例页面。**这是多团队并行的前提**。
2. **`cargo xtask gen-crud <schema.table>`** —— 读 `information_schema` 反生成 Rust 实体 + repo + service + handler + Vue 列表/表单页 + 迁移 + 权限点。对标若依代码生成器，但产出是符合本架构约定的代码。
3. **OpenAPI 单一契约**：`utoipa` 注解 → `/api/openapi.json` → `openapi-typescript` 生成前端类型 → 前后端不再手抄字段。
4. **sqlx 离线编译**：`.sqlx/` 入库，CI 无需连库；本地 `docker compose up pg` 后 `cargo sqlx prepare`。
5. **测试分层**：
   - 单测：纯领域逻辑（无 IO）。
   - 集成：`sqlx::test` 自动建库跑迁移 + 事务回滚，每个插件自带。
   - 契约：`insta` 快照 OpenAPI，防破坏性变更。
6. **编译加速**（Rust 团队必做）：`sccache` + `lld`/`mold` + `cargo nextest` + dev profile `debug=1`；workspace 拆 crate 本身就有助于增量编译。
7. **CI 门禁**：`fmt` → `clippy -D warnings` → `test` → `sqlx prepare --check` → 前端 `tsc --noEmit` + `eslint`。

## 11. 部署

```yaml
# 交付形态一：单二进制（推荐私有化）
server:  # rust 静态链接 + rust-embed 内嵌 Vue dist
  image: registry/admin-server:1.2.3
  ports: ["8080:8080"]
  environment: [DATABASE_URL, REDIS_URL, S3_ENDPOINT, ...]
pg:      postgres:16-alpine
redis:   redis:7-alpine        # 可选
minio:   minio/minio           # 可选
```

- 健康检查：`/healthz`（存活）、`/readyz`（DB/依赖就绪）。
- 优雅停机：`axum::serve(...).with_graceful_shutdown()`，等 in-flight 请求与任务 drain。
- 配置：`config/default.toml` + `config/{env}.toml` + 环境变量覆盖（figment）。
- 私有化交付：一个二进制 + 一个 PG，客户现场 `docker compose up` 即可，这是 Rust 相对 Java 的最大优势之一。

## 12. 里程碑（建议按此推进，每阶段可交付）

| 阶段 | 周期 | 交付物 | 验收标准 |
|---|---|---|---|
| **M0 骨架** | 2–3 周 | workspace、kernel（config/error/log/trace/db/迁移/health）、Vue 登录页 | `docker compose up` 后能登录，OpenAPI 可访问 |
| **M1 系统管理** | 3–4 周 | 用户/角色/菜单/部门/字典/参数/审计日志、RBAC 全链路、数据权限 | 对标若依系统管理模块功能可用 |
| **M2 插件机制** | 2 周 | `Plugin` trait + inventory 装配 + `xtask new-plugin` + demo 插件 + 前端聚合 | 新建一个插件不改内核即可跑通 CRUD |
| **M3 生产力** | 3 周 | `xtask gen-crud`、文件、定时任务、通知、导入导出 | 一张新表 10 分钟出全套 CRUD |
| **M4 企业化** | 3 周 | 多租户 RLS、可观测（OTel+Prometheus）、Docker 交付、压测 | 单机 500 并发管理后台操作 P95 < 200ms |

> 工作流（审批流）**不在前四期**：先用"状态机 + 任务表"做轻量审批；真需要 BPMN 时外挂 Flowable/Temporal，别自研。

## 13. 风险与反模式（血泪清单）

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 用 dylib / abi_stable 做插件热插拔 | 类型不兼容、UB、无法卸载 tokio 任务 | 编译期内嵌；要隔离就 WASM 或独立进程 |
| 一上来拆微服务 | 事务、调试、部署成本爆炸 | 模块化单体，按判据再拆 |
| 自研 BPMN 工作流引擎 | 无底洞 | 状态机够用；否则外挂成熟引擎 |
| `anyhow` 直接返回给 handler | 错误码无法收敛，前端无法处理 | `thiserror` + 统一 `AppError` |
| 菜单在前端硬编码 | 前后端两处维护，权限对不上 | 后端下发菜单树，前端只做组件映射 |
| localStorage 存 JWT | XSS 即账号接管 | HttpOnly Cookie + CSRF |
| 字符串拼接 SQL 做数据权限 | SQL 注入 + 权限绕过 | `sea-query` 绑定参数 |
| 所有插件共用 `public` schema | 表名冲突、迁移互相阻塞 | schema-per-plugin |
| 跨插件直接调 service | 插件耦合，无法独立发布 | 领域事件 / outbox |

## 15. 一句话总结

> **内核薄、契约硬、插件胖**：内核只提供"装配 + 横切能力 + 系统管理"，所有业务一律做成 crate 插件，靠 trait 与 schema 边界强制解耦；交付是单二进制，扩展靠加 crate 而不是改内核。

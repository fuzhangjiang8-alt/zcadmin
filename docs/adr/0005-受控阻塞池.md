# ADR-0005：受控阻塞池（限流的 spawn_blocking）

- 状态：已采纳（2026-11-06）
- 相关代码：`crates/kernel/src/blocking.rs`、`crates/kernel/src/password.rs`
- 相关文档：`docs/01-后端架构.md` §1.1 线程模型、§18 性能与容量

## 背景

系统里有两类**同步、重 CPU/重内存**的操作：

| 操作 | 单次成本 | 触发入口 |
|---|---|---|
| Argon2id 密码校验/哈希 | 约 19 MiB 内存 + 40~60ms CPU | 登录、改密、建用户、建租户、批量导入 |
| xlsx 解析/生成 | 视文件大小，10~500ms CPU | 用户导入、各类导出 |

改造前的写法是**直接在 async handler 里同步调用**。后果：

1. tokio worker 线程（默认 = CPU 核数）被占满 → 事件循环停摆 → 所有请求一起卡住；
2. 早高峰 200 人同时登录 → 200 × 19 MiB ≈ 3.7 GiB 瞬时内存，容易 OOM。

## 决策

新增 `kernel::blocking::run`：

- 内部用 `spawn_blocking` 把工作移出 worker；
- **外层加信号量**，默认并发 4（`BLOCKING_MAX_CONCURRENCY`，上限 32）；
- 排队超过 3 秒返回 `BlockingError::Busy` → 映射为 **503 + `Retry-After`**；
- 任务一旦开始执行不可取消（调用方应在拿到结果后再写库）。

密码相关统一走 `password::hash_password_async` / `verify_password_async`。

## 备选方案

| 方案 | 不选原因 |
|---|---|
| 直接用 `spawn_blocking` | **不解决并发**：tokio 阻塞池默认上限 512，`512 × 19 MiB` 同样打爆内存 |
| 用 `tokio::task::block_in_place` | 只适用于 multi-thread runtime，且会把 worker 线程转成阻塞线程，等于减少 worker 数量 |
| 降低 Argon2 参数（m/t） | 直接削弱密码存储强度，安全优先级高于性能（见 NFR 排序） |
| 把哈希外包给独立服务 | 引入新组件与新故障点；当前规模不值得 |

## 影响

- 过载时登录相关接口会返回 503 而不是"很慢但最终成功"。这是**有意为之**：
  排队只会让所有请求的尾延迟一起恶化。
- 监控口径：`BLOCKING_MAX_CONCURRENCY` 打满时会在日志里出现
  「并发上限已满 / 阻塞任务排队超时」，应作为容量告警，而不是当成 bug。
- 新增重 CPU 操作时必须走 `blocking::run`，**不允许**直接 `spawn_blocking`
  （`cargo xtask arch-check` 目前未强制，靠评审把关）。

## 回滚

把 `password.rs` 的 `*_async` 调用换回同步版本即可；`blocking::run` 可保留（无副作用）。
回滚后必须同步在 `docs/01` §1.1 记录"接受 worker 被 Argon2 阻塞"的风险。

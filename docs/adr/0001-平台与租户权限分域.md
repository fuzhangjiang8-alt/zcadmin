# ADR-0001：平台权限与租户权限分域

- 状态：已采纳（2026-11-02）
- 相关迁移：`crates/kernel/migrations/0067_platform_permission_scope.sql`、`0068_rls_association_tables.sql`
- 相关代码：`crates/kernel/src/system.rs`、`crates/kernel/src/auth.rs`

## 背景

多租户版本上线后暴露出两个越权路径：

1. `create_tenant` 把新租户的管理员写成 `sys_user.is_super = true`。登录时
   `is_super` 会展开为通配权限 `*`，于是**任何租户管理员都能调用
   `/api/system/tenants`**，列出、停用、删除、物理清理其他租户。
2. `sys_permission` 没有「归属层级」，`list_permissions` 返回全部权限点，
   `set_role_permissions` 只校验角色属于本租户、不校验权限点归属。
   即使修好第 1 点，租户管理员仍可给自己的角色授予 `system:tenant:*` 完成提权。

同时 `sys_user_role` / `sys_role_permission` / `sys_user_post` 三张关联表
既没有 `tenant_id` 也没有 RLS，`set_user_roles` 未校验目标用户归属。

## 决策

### 1. 权限点增加 `scope`

`sys_permission.scope ∈ {platform, tenant}`，默认 `tenant`：

- `platform`：仅平台超管可见、可授。当前只有 `system:tenant:*`（租户管理/账单）。
- `tenant`：租户管理员可授，包含系统管理与全部插件权限。

`list_permissions` 按调用者身份过滤；`set_role_permissions` 校验每个 ID
是否存在且可授，越界返回 422。

### 2. 平台超管 = `is_super`

保留 `is_super` 作为**平台级**标志，只有种子管理员（默认租户）拥有。
`create_tenant` 创建的管理员改为 `is_super = false`，同时自动创建
`tenant_admin` 角色（`data_scope = all`）并授予全部 `tenant` 级权限。

判定函数：`CurrentUser::is_super_admin()`（权限集含 `*`）。
带 scopes 的访问令牌不算平台超管——这正是期望行为。

### 3. 关联表用「父表可见性」做 RLS

不给三张关联表加 `tenant_id`，而是让策略引用父表：

```sql
CREATE POLICY tenant_isolation ON sys_user_role
    USING (user_id IN (SELECT u.id FROM sys.sys_user u))
    WITH CHECK (user_id IN (SELECT u.id FROM sys.sys_user u));
```

`sys_user` / `sys_role` 本身就是 FORCE RLS，子查询天然被租户过滤，
避免两处租户字段漂移，也不需要回填。

### 4. 写路径显式校验

`set_user_roles` / `get_user_roles` 增加 `ensure_user_in_tenant`，
角色绑定逐个 `ensure_role_in_tenant`。RLS 是兜底，应用层校验给出明确的 404。

## 代价

- 租户管理员少了「租户管理」入口（符合预期）。
- 存量租户在 0067 迁移里被自动降级并绑定 `tenant_admin`；
  迁移逐租户 `set_config('app.tenant_id')`，可在 FORCE RLS 下执行。
- 关联表策略每行带一个主键子查询；RBAC 表数据量小（百级），可接受。

## 备选方案

| 方案 | 否决原因 |
|---|---|
| 给关联表加 `tenant_id` 并回填 | 需要改所有写入点，回归面大；且两处租户字段可能不一致 |
| 用独立的 `platform_admin` 布尔列 | 与 `is_super` 语义重复，历史数据迁移更复杂 |
| 只在 handler 里加 `is_super` 判断 | 无法防止「授权界面」层面的越权，且容易漏接口 |

# 06 · 平台化演进：中台与多产品

本文只保留既有演进边界和触发条件，不作为当前功能清单或立即建设计划。现有能力/差距见10，架构决策仍需人工评审。

## 1. 何时抽公共能力

一项能力进入中台须同时满足：至少两个产品真实复用、不含单一业务语义、有明确owner和SLA。
先跑通产品，再抽身份、租户、权限、审计、文件、配置等共性；客户/订单/设备业务状态仍归产品。
不同时搭建全部产品、注册中心、消息骨干和多种数据库，避免只有平台没有可用产品。

## 2. 扩展层级

| 形态 | 适用 | 边界 |
|---|---|---|
| crate插件 | CRM、审批、报表等同事务业务 | 编译期装配，本域schema，复用kernel |
| 服务型扩展 | 长连接、推理/GPU、设备高吞吐 | 独立资源/故障域，只依赖公开契约 |
| UI扩展 | 独立产品页面/工作台 | 当前构建期聚合，热加载/微前端需另行建设 |

L1中台不依赖L2产品；产品之间通过公开契约/事件协作；客户端不直连数据库。
现有Plugin trait不包含服务发现、事件总线或资源调度，不能因文档有层级就假定已有运行设施。

## 3. 产品接入重点

| 产品 | 新增复杂度 | 必先明确 |
|---|---|---|
| CRM | 业务事务、权限与流程 | 数据范围、状态、幂等、报表/导入导出边界 |
| IoT | 设备接入、持续写入、时序 | 一机一密/证书、协议、设备归属、背压、固件签名 |
| IM | 长连接、消息投递/离线/多端 | 顺序、确认、重复、重连、存储与推送权限 |
| AI | 流式推理、GPU、计量与成本 | Python推理服务owner、租户配额、取消、超时、数据/提示词安全 |

连接/推理/采集层不能直接塞进管理后台worker。通信、计量和用户业务采用公开身份/租户模型，不各建一套隔离体系。

## 4. 数据与存储演进

PG优先，先治理索引、分区、归档、连接与慢查询；新增存储同时增加备份、权限、监控与恢复成本。
原有评估阈值为单表约1亿行或写入超过5000 TPS；这是启动评估的条件，不是自动切库规则或已验证容量。
时序、搜索、向量、分析库按真实负载评审；业务DB是状态真相源，索引/缓存可重建，双写失败必须有补偿/对账。
大租户独立schema/库须有导出回填、校验、切流和回退计划。

## 5. 事件与开放契约

既定方向为CloudEvents、事件schema只增兼容、Outbox同事务入箱、至少一次与消费者幂等；当前无完整通用实现。
建设前明确event id、tenant、source/type、版本、顺序、敏感字段、重试/死信/重放；禁止跨插件直接依赖代替事件。
API采用OpenAPI及统一错误码，破坏性变更走版本/宽限期。OIDC/SSO、SCIM、ABAC、服务注册中心等属于独立需求，不默认为已提供。

## 6. 推进顺序与准入

1. 基础内核与一个业务域形成权限、数据、审计、部署闭环。
2. 第二个产品接入时复用已有能力，只补实际缺口。
3. 出现资源或团队边界，再拆服务；服务数超过20时才评估服务网格需求。
4. 每次扩展先给规格、数据/安全契约、容量与成本预算、owner、降级/回滚及验收证据。

多语言必须有可持续owner，AI允许Python不意味着可任意引入语言。跨域接口由owner评审，资源用量按租户计量，防单租户耗尽共享资源。

## 7. 不做与风险

不自研BPMN/消息中间件/报表引擎，不为热插拔引入不稳定ABI；前端、存储和服务拆分不以「未来可能用到」为依据。
过早平台化、核心团队成为排队瓶颈、多存储/多语言失控、事件漂移与AI成本失控均需在规格中给具体约束。
